Who Calls Whom: Understanding LLM Agents Through CSP and Coroutines

In this seriesRuntime Architecture of LLM Agents · 2 / 2 · Control Flow

Instead of understanding LLM agents as models calling tools, we can view them as systems made up of communicating processes and coroutines; this perspective better explains event sources, control transfer, suspension, and recovery.

In an event-driven agent system, we need a different way to think about “who calls whom.” Traditional function calls focus on caller and callee. An agent runtime cares more about where events come from, who consumes them, when control is yielded, and under what conditions another computation begins.

Many LLM agent frameworks still use a call/return picture: the user makes a request, the model proposes a tool call, the tool returns a result, and the model continues reasoning. That picture is clear and works well for short, clearly bounded one-off operations.

The problem begins when control flow is no longer one line. A tool may run for a long time, logs may keep arriving, the user may intervene, and background work may generate events independently. Instead of asking only whether the model is the “main program,” it becomes more useful to ask: who produces events, who consumes them, who owns the relevant state, and who decides what happens next?

Communicating Sequential Processes (CSP)1 and coroutines2 provide two views at different levels. CSP is a model of communication and concurrency: independent processes cooperate through messages. Coroutines are closer to an execution mechanism: an execution unit can suspend while waiting, return control to the runtime, and later continue. They do not replace one another, but both help explain control flow that does not fit a single call stack.

Is the Model the Main Program?

In a traditional program, the main program controls execution order. It calls a function, waits for the return value, and then proceeds. If we apply that picture to agents, we get an intuitive model: the large language model is the main program, and tools are functions it calls.

That intuition is only partly true. The model does make tool requests and continue planning based on tool results. But in an event-driven system, many things are not initiated by the model. Users may enter new instructions at any time. Tools may emit result events when they finish. Observers may wake the planner when they detect anomalies. Schedulers may trigger tasks when time conditions are met. The model is not the only starting point, and it should not be forced to act as the only control center.

The model is better understood as a planner, not a main program. It interprets what events mean for the goal, decides whether to keep waiting, ask the user for confirmation, submit a tool task, adjust the plan, or terminate the flow. It is not the top of a single call stack. It is a high-level process in an event system.

The Perspective of Communicating Processes

The core of CSP is not function invocation but cooperation among independent processes through messages. In this article, lowercase process means a communicating process in the CSP sense: a participant that can make progress independently and exchange messages with other participants. It describes communication and control flow, not a lifecycle category.

That distinction matters because Structured LLM Design uses capitalized Process for a different concept: an activity whose lifetime may extend beyond the scope that created it. A CSP-style process can still be scoped to a caller; using messages or channels does not automatically make an activity a lifecycle Process.

From the communication perspective, a user interface, planner control process, tool executor, log observer, scheduler, or external service can all be modeled as participants that independently produce or receive messages. This is an abstraction: they do not have to be implemented as the same kind of operating-system process, coroutine, or task.

These participants can exchange events through channels or other message mechanisms. User actions, tool requests, tool results, logs, and observations may follow different paths. The important point is not to invent a new top-level type for every message; it is that sender and receiver do not have to share one call stack or be running at the same time.

A typical flow therefore does not have to be written as “the user calls the model, the model calls the tool, and the tool returns.” The interface may first emit an operation event; the runtime updates state and wakes the planner when planning is needed; the planner issues a tool request; the tool executor keeps producing state changes while it works; and the observation layer decides which changes are worth turning into a new observation.

Short operations can still use ordinary calls. Long-running activities can expose events as they progress. Tool completion, log updates, additional user input, and scheduled triggers may all become event sources. The planner is not a main function sitting above every component. It is a decision component that the runtime invokes when high-level interpretation or planning is needed.

This view is particularly useful when several event sources progress independently: long-running work, continuous service logs, mid-task user input, or device feedback. A single call stack expresses these relationships poorly; explicit message boundaries make it clearer who produces state, who consumes it, and who can wait independently.

Why Log Streams Fit the Communication Model

Log streams show the value of this model especially clearly.

In the traditional picture, the planner seems to actively call the logging system and wait for a chunk of logs to return. But services do not wait for the model to call before they produce logs. The service is already running, and logs are already being produced. A log observer should continuously read the log stream and send observation events to the planner when it finds content related to the current action.

This means the planner does not need to monitor the logging system directly. It only waits for important observations. The log observer decides which logs are relevant to the current task and which are background noise; which lines show ordinary progress and which indicate an error, timeout, or need for replanning.

That is the advantage of the communication model. Each process runs on its own, handles local input, and sends information to other processes only when necessary. The planner does not have to read every raw signal or repeatedly poll every component. It handles only events that matter for decisions.

In this structure, the observer itself is an independent process. It is not a smaller planner. It monitors, filters, and reports. It continuously consumes log streams or tool output and sends compressed state changes to the planner.

Control Transfer Through Coroutines

Coroutines provide a view closer to implementation. An execution unit can suspend while waiting for a result, return control to the runtime, and later continue when the condition it needs becomes available. Coroutines can implement CSP-style communicating processes, but a coroutine does not itself define the system’s communication semantics.

A high-level planning coroutine can suspend when there is no observation worth handling. When a relevant observation arrives, it invokes the language model, obtains an action, and dispatches that action to the appropriate executor. While a tool result is pending, the related coroutine can wait without stopping the runtime; observers, executors, UI handlers, and schedulers can continue to run.

Tool executors can also be expressed with coroutines: wait for a request, start work, emit progress, and eventually emit a result. Observers consume logs or state updates; schedulers wait for time conditions. In each case, waiting can yield control back to the runtime.

Code written with coroutines can look sequential—“await an event, then continue”—but the system is still event-driven. Waiting suspends one execution unit rather than freezing the entire system.

One caution matters for LLM systems: suspension and resumption in the runtime do not imply that the same model invocation remains alive for ten minutes and later resumes from an internal machine stack frame. For an activity that outlives one invocation, a more natural shape is:

Invocation A
    │
    └── start long activity
            │
            └── handle returned

Invocation A ends
activity continues
            │
            └── Completed event
                    │
                    ▼
                  runtime
                    │
              new observation
                    │
                    ▼
              Invocation B

Invocation A does not “come back to life.” The external world changed, the runtime formed a new observation, and a new computation began. This distinction is especially important for long-running CI, deployments, and remote jobs.

There Is No Fixed Initiator

The traditional structure can be summarized as: a main program calls the language model, the model calls a tool, the tool returns, and the model continues. That picture puts the model at the center and compresses interaction into one line.

In an event-driven system there is no permanently fixed initiator. User input may start one round of work; a tool completion may produce a later event; an observer may report an anomaly; a scheduler may fire on time; an external service may change state independently. Each concrete event has a source, but the language model is not always at the start of the chain.

This lets model computation stay concentrated where semantic judgment is valuable: whether an error affects the goal, whether new user input changes a constraint, whether a tool result is sufficient to proceed, or whether an anomaly needs confirmation. Collection, transport, aggregation, and simple filtering of events can remain ordinary program logic.

The more natural center is therefore the runtime’s event handling and state update mechanism rather than one model invocation. The planner handles high-level decisions; tool executors handle external work; observers handle logs and state changes; schedulers handle time; and the interface handles user input.

The planner also does not need to poll everything continuously. The runtime can receive user events, observations, tool results, and scheduled events, update state, and then decide whether the planner needs to become involved. Not every event should directly trigger a model call.

Go’s select is a useful control-flow analogy: a runtime can wait on several channels and handle whichever input becomes ready. The analogy stops there. Readiness says an input can be processed; it does not say that the input has decision value, nor does it specify fairness or scheduling policy.

Long-Running Tools Should Start an Activity and Return a Handle

Short tool calls do not need to abandon call/return. A different control-flow representation is useful for activities that keep producing state or need to progress independently.

Instead of holding the caller at “wait for the final return value,” the runtime can start the activity and return a stable handle. The model is then expressing “start this activity” rather than “call this function and immediately give me its final result.” The activity may later produce progress, logs, intermediate results, errors, or completion events.

The planner can keep waiting, cancel, retry, switch strategies, or replan when a new observation matters. Progress can be processed incrementally; cancellation can be sent independently; observers can trigger recovery; and several activities can make progress concurrently.

This change moves waiting out of the model call chain. The runtime can handle other events while the activity continues, and decide whether to invoke the planner again on completion, failure, timeout, cancellation, or another important observation.

The terms activity and handle here describe control flow only. They do not by themselves decide whether the activity is a scoped Task or a lifecycle Process. That classification depends on ownership and lifetime, not on whether the activity uses events or a handle.

Control in an Environment Whose State Is Not Fully Visible

One step further, an agent runtime can be viewed as a system making decisions in an environment whose full state is not directly visible. The runtime only updates its judgment from user input, tool results, logs, metrics, and sensor feedback. Control theory, robotics, and partially observable decision models use related ideas. The only property borrowed here is that the system learns about the environment indirectly through observations.

The planner is not simply mapping one input to one output. It receives observations, updates an assessment of the environment, and chooses another action. After that action, the environment changes and produces more evidence.

This has a limited similarity to robotics: neither system receives a perfect, complete view of the world. Logs, tool results, and user actions are evidence sources, but no single source is the entire state.

For an agent that operates continuously in a changing environment, “input in, output out” describes only one computation. The larger loop is observe, update the assessment, act, and observe again. The model performs high-level planning; the runtime is responsible for turning feedback into reliable events and observations.

Conclusion

For agent systems that include language models, tools, log streams, user behavior, and automated actions, a single synchronous call chain becomes increasingly awkward. It does not naturally express long-running work, streaming output, continuous logs, concurrent operations, or environmental feedback.

A better view is an event system in which several activities can progress independently. The user interface, tool executors, observers, schedulers, and planner can be treated as communicating participants; the implementation may use coroutines, tasks, threads, or other mechanisms. The language model performs high-level planning but is not the only “main program.”

CSP explains how independent processes communicate through messages. Coroutines explain how one execution unit can yield control while waiting and later continue. These views operate at different levels, but both show why one linear call/return chain is insufficient once an agent faces several asynchronous sources of change.

This article is about communication and control flow, not lifecycle classification. Being asynchronous, streaming, channel-based, or modeled as a CSP process does not automatically make an activity a capitalized Process. In the lifecycle model used by Structured LLM Design, that term has one decisive criterion: can the activity continue after the scope that created it has ended?

Once long-running tools expose state through handles, logs are compressed into observations, and user input or scheduled triggers also enter the runtime, “who calls whom” no longer has one permanent answer. More useful questions are: where did this event come from, who owns and updates the state, which execution unit yields while waiting, and what condition causes the next computation to begin?
