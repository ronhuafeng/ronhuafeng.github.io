From Tool Calls to an Event-Driven Runtime: The Runtime Architecture of LLM Agents

In this seriesRuntime Architecture of LLM Agents · 1 / 2 · Architecture

LLM agents should not be understood as a chain of tool calls; as tasks grow longer and environments become more complex, the runtime needs an event-driven architecture for state, concurrency, observation, and recovery.

Many large language model agent designs still assume a simple flow: the model proposes a tool call, the tool runs, a result comes back, and the model continues reasoning. That call/return model works well for short, clearly bounded operations. The problem begins when tool execution and the external environment keep changing over time.

Real tools are often less tidy. Some stream logs, some produce intermediate results, and some merely start an external activity that continues on its own. Users may keep interacting with the system, revise requirements, or trigger other services while work is still in progress. An agent can also do more than produce text: it may create tasks, call external services, or control devices.

In those settings, “the model calls a tool and the tool returns” is no longer enough to describe the system. A more useful design is an event-driven runtime: tools, logs, user actions, scheduled work, and sensors can all produce events; the runtime receives and organizes those changes; and the language model is invoked when higher-level judgment is needed. The model is better understood as an on-demand planner than as the sole center of control flow.

The difficult part is not making more tool calls. It is turning continuous, asynchronous, noisy changes into state that is useful for decisions.

Tool Calls Are Not Single Function Returns

Queries, format conversions, and one-shot computations fit call/return well. The problem is work that keeps progressing: a tool may run for a long time, keep producing intermediate state, or wait on another system. If an interface exposes only “start” and “final return,” the runtime cannot see what happens in between and has little opportunity to react.

Code execution can keep printing output. Browser automation moves through loading, waiting, failure, and retry. Model training, data processing, literature review, and service deployment may all run for a long time. A robot likewise changes state continuously and produces feedback while acting.

For long-running activity, forcing the planner to wait for a final result makes it hard to notice a hang, an error, a departure from the goal, or a new decision opportunity. But waking the model for every line of output creates the opposite problem: logs fill the context and reasoning is spent on changes that do not matter.

A better abstraction is an activity whose state can be observed while it progresses. It may emit events such as started, progress updated, stage completed, errored, waiting, completed, or canceled. The planner should not consume every raw event. An observation layer should filter and compress changes that may affect a decision.

Three mechanisms work well together. First, use event delivery so the runtime notices new state promptly. Second, throttle and aggregate high-frequency output so every fragment does not become a planning event. Third, keep low-frequency reconciliation: periodically check important state so lost callbacks, broken connections, delayed logs, or state drift do not remain invisible.

Event delivery and periodic checking are therefore complementary. Push gives low-latency notice that something changed; reconciliation checks that important state still exists and helps detect missed events. Neither one means the language model should be called immediately.

A useful boundary is:

raw signal
    ↓
runtime event
    ↓
filter / aggregate / correlate
    ↓
observation
    ↓
does this change a decision?
    ↓
planner invocation

A new CI log line may update runtime state without triggering a full reasoning step. Several lines that together establish “the test failed” can become an observation worth handing to the planner. Events wake the runtime; observations wake the model.

An Observer Is Not a Smaller Planner

This architecture needs an observer. The observer may be implemented with rules, a smaller model, or a language model in more complex cases, but it should not be designed as a free-form miniature planner. Its responsibility should stay narrow: decide whether the task is still running, whether an error has appeared, whether a stage boundary has been reached, whether the planner needs to intervene, and how to compress continuous output into structured state.

The planner is responsible for goals, strategy, and replanning. The observer is responsible for sensing, monitoring, alerting, and summarizing. The clearer this boundary is, the more stable the system becomes.

A capable observer should not pass large logs to the planner verbatim. It should produce a state packet that answers questions such as: what stage is the task in; what has changed since the last report; is there an anomaly; does the planner need to decide; if so, what candidate actions exist; and what minimal evidence supports that judgment.

The raw stream should still be kept for audit and debugging. But in normal operation, the planner should consume structured state and semantic summaries, not the raw stream itself. Only when deeper diagnosis is needed should the system go back to the original records.

There is a useful analogy with human perception. When walking or driving, a person can think about other things while relying on vision and low-level reactions to avoid obstacles. Higher-level cognition does not process every visual frame. Only important changes need conscious attention. Agent systems should work in a similar way: lower layers continuously sense and quickly filter, while higher layers handle changes that matter to the goal.

But the analogy is only a guide. It cannot replace engineering design. Human low-level reactions are supported by a large body of prior knowledge built up over time. An agent system must explicitly define what counts as an anomaly, what counts as progress, and what should be escalated. The lower the layer, the more it should rely on clear rules, state machines, format checks, and thresholds. Open-ended reasoning belongs higher up.

Long Tasks Need Decision Points, Not Blind Waiting

For long-running tasks, the key question is not how long to wait. It is when to decide again. The situations that arise during a task can be grouped into four categories.

The first is normal progress. The task is producing output, making progress, and showing no anomaly. The planner should not intervene frequently here. The observer only needs to maintain heartbeat and stage summaries.

The second is a local update. A tool produces new logs, an intermediate image, or a partial result, but the information is not enough to change the plan. The system updates task state without asking the planner to reason through the situation again.

The third is a decision point. The task reaches a branch: multiple results appear, extra parameters are required, a new constraint is discovered, a checkpoint is reached, or the current evidence is insufficient for automatic progress. The observer should compress the relevant context and hand it to the planner, which then decides the next step.

The fourth is an abnormal condition. The task is stuck, times out, fails repeatedly, consumes unusual resources, drifts away from the goal, or creates a safety risk. The system may need to interrupt, retry, roll back, switch tools, ask the user for confirmation, or terminate the task.

Managing long tasks means identifying a small number of points in a continuous process where a decision is useful. Without those distinctions, the planner either waits blindly or gets interrupted by low-value signals.

Observation frequency should not be fixed either. When a task starts, changes are often frequent, so the system can observe more frequently. During stable execution, the rate can drop. As a timeout or important checkpoint approaches, or signs of trouble appear, the observation rate can rise again. This risk- and change-based observation pattern fits real systems better than simple periodic polling.

Logs from Long-Running Services Should Be Sliced by User Action

Another important case is a service that keeps running. It continuously produces logs, some of which relate to user actions. After a user acts, the planner needs enough evidence to understand what happened and decide what comes next.

The goal is not simply to “let the model read logs.” The system needs a traceable relationship among the user action, service state, relevant log fragments, and later planning. Request IDs, session IDs, trace IDs, and time windows can narrow the evidence, but they do not by themselves prove causation.

Each user action should therefore leave an action record. At minimum it should say what the user did, which service or resource it targeted, and what effect was expected; when available, it should also preserve request, session, or trace identifiers. The system can then open a bounded observation round around that action.

An observation round does not watch the whole log stream forever. It collects evidence from relevant components and a relevant time range. After a “deploy” action, for example, it may focus on the deployment service, scheduler, dependency fetches, and health checks rather than every background heartbeat. It can end once there is sufficient success or failure evidence, on timeout, or after a period without relevant new information; the exact stopping rule belongs to the task semantics.

This turns a continuous stream into small, action-related slices. The planner receives a bounded account with a starting point, evidence, and current state rather than an unbounded ocean of logs.

The observer selects relevant logs, decides when the observation round is complete, compresses the evidence, and decides whether to escalate to the planner. Its output should be a limited conclusion: whether the action appears to have taken effect; whether the current state is success, failure, in progress, or uncertain; which stage may contain the anomaly; and what evidence is still missing.

Logs are not a complete source of truth. They may be missing, delayed, out of order, or say “success” while the actual state did not change. Important judgments should therefore be checked against metrics, state queries, UI observations, database reads, or API results when appropriate. A more reliable sequence is: collect evidence around the action, form a state judgment, verify the critical parts, then let the planner choose the next step.

The runtime also needs background health monitoring that is independent of any one user action. Queue buildup, resource exhaustion, session expiration, or failed background work can emerge gradually. Action-scoped observation and background monitoring handle different sources of change and should not be conflated.

Responding to the User Is More Than Producing Text

An agent’s response should not be understood as “reply with a sentence.” Text is only one kind of action. The system may need to explain something, speak aloud, generate a report, call an external service, create a scheduled task, place an order, control a device, or direct a robot.

At the runtime scheduling layer, these outputs can be represented uniformly as actions: send a message, call an API, create a task, or control a device. That common control-flow representation does not mean they have the same risk or authorization semantics.

Informational actions mainly change what the user knows: text, tables, reports, progress updates, or speech. Other actions change software state, such as sending email, editing a document, calling a service, or running a script. Device and robotic actions can change the physical environment. The latter classes usually need stronger authorization and validation.

When one goal requires several outputs, a structured action plan is easier to execute and audit than a single free-form paragraph. A goal might include producing a literature summary, showing it to the user, and creating a reading reminder. The actions belong to one plan but can be handled by different executors.

Authorization should depend on the action’s side effects and risk. Which operations may run automatically, which require confirmation, and which are disallowed should come from product policy, user authorization, and resource scope rather than from one universal rule.

A clean division of responsibility is: the planner proposes what to do; the policy layer decides whether this instance is allowed; the execution layer turns the action into a concrete operation; and the observation layer feeds the result back into the runtime.

The Runtime as an Event-Driven Concurrent System

In implementation terms, this runtime is closer to an event-driven concurrent system than to a synchronous call chain. Users, tools, observers, schedulers, and executors can all produce and consume events. The language model sits at a higher decision layer and is invoked when an important change needs interpretation, goal adjustment, or a new plan.

“Event-driven concurrent system” is only a structural description. It means that tools, observers, schedulers, and executors do not have to share one linear call chain. This article focuses on how events enter the runtime, how they become observations, and when the planner should be invoked again.

A separate control-flow question remains: who waits, who resumes, and who owns control at each point? Communicating processes and coroutines are useful lenses for that question, which is developed in the companion article.

A Unified Runtime Structure

Putting these pieces together gives a clearer picture of an LLM agent runtime.

At the bottom are the environment and tools: external services, logging systems, document systems, web pages, robots, databases, and automation interfaces. They produce events and receive action requests.

The middle layer contains executors, observers, and schedulers. Executors turn action plans into concrete operations. Observers extract meaningful changes from logs, tool output, state queries, and environmental feedback. Schedulers handle one-off or periodic work. Together, these components maintain runtime state.

At the top is the planner. It does not watch every raw output or perform low-level monitoring. It receives compressed observations, maintains an assessment of goals and environment, and chooses the next action when the goal changes, a plan branches, an anomaly needs handling, or new information has enough decision value.

The user is both an input source and someone affected by the system’s actions. The agent can explain state, request confirmation, report progress, show results, speak, or perform authorized external operations. The user is part of the interaction environment, not merely an observer outside it.

As an intuition, this can be viewed as two different speeds of feedback: a faster layer for sensing, state maintenance, and low-risk reaction; and a slower layer for goal interpretation, strategy changes, and complex decisions. This is a distinction in responsibility and decision frequency, not a requirement that the implementation contain two literal loops.

This article answers two questions: how events enter the runtime, and what changes are worth handing back to the planner. It does not define activity lifetimes. Short calls, scoped concurrency, and activities that can outlive their caller need a separate lifecycle model; that distinction is developed in Structured LLM Design: Organizing an Agent Runtime by Lifetime.

Conclusion

The key to LLM agents is not simply making the model better at calling tools. It is redesigning the relationship among tools, observation, action, and planning.

Short, bounded operations can remain ordinary call/return. Long-running activities need observable state, and high-frequency changes should be compressed into a small number of observations that are worth a decision. Logs should be tied to concrete actions and system state rather than dumped indiscriminately into model context.

The language model does not need to hold all control. It is most useful when a semantic change, planning branch, anomaly, or new constraint needs interpretation. The runtime receives ongoing changes, maintains state that can be checked, and hands only the important ones to the planner. The planner chooses an action; the execution layer carries it out; the observation layer brings the result back.

An event-driven runtime answers how an agent system should be organized. The next question is how control moves inside such a system: who produces events, who waits, who yields, and what causes another computation to begin. That question is better examined through communicating processes and coroutines.
