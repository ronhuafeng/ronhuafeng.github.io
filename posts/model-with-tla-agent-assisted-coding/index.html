在 Agent 辅助编程中引入 TLA+：并发与生命周期正确性的建模与有界验证

本文讨论在 Coding Agent 工作流中引入 TLA+ 模型检查的方法与效果：以过期回调问题为例给出最小模型、反例与修复，分析负向见证对模型判别性的作用，并结合两个实际案例说明，建模主要承担发现问题的职能，TLC 则为修复提供有限配置内的穷举结论。

1 问题

异步与并发系统中存在一类缺陷：每个函数在顺序执行下都正确，错误只在特定的事件交错下出现。典型情形如下。一个后台操作针对资源 worker-A 启动；操作完成之前，该资源被删除并以同一名称重建；随后旧操作的回调到达，提交逻辑只比较名称，于是把旧结果写入了新资源（图 1）。

图 1：过期回调写入新资源的事件时序。

为区分同一逻辑名称下先后存在的实体，本文把其中每一代称为一个 incarnation。上例中，回调携带的是为第 1 代计算的结果，提交时资源已经是第 2 代。缺陷的成因不在某一条语句，而在于授权条件随时间失效：结果生成时具有写入权限，到提交时，这一权限已随资源替换而失效。

以测试为中心的反馈循环难以稳定覆盖这类缺陷。测试只执行被显式构造的事件顺序，而可能的顺序随参与者和动作数量组合增长；如果开发者或 Coding Agent 没有预见到“启动、替换、回调、提交”这一顺序，对应的测试就不会存在。模型检查采用另一种方式：先给出系统的状态、改变状态的动作以及不允许出现的状态，再由 TLC 在有限配置内枚举全部可达状态（图 2）。

图 2：测试执行选定的场景，TLC 枚举有限模型的全部可达状态。本图为示意，不代表覆盖率统计。

本文讨论如何把 TLA+ 引入 Coding Agent 的工作流，所述方法已整理为 Agent Skill model-with-tla1。本文的论点有两个。第一，建模过程迫使 Agent 为“已派发”“提交权限”“清理责任”等概念给出精确定义，以这些定义对照实现，是发现问题的主要途径。第二，TLC 的主要作用体现在修复之后：它在给定的有限配置内，对全部事件交错给出穷举结论，回答测试难以回答的问题，即在该范围内是否还存在未被预见的违例顺序；负向见证则用来确认这一结论不是空洞的。

第 2 节以一个最小模型演示完整流程；第 3 节讨论模型的判别性与负向见证；第 4 节给出两个实际案例；第 5 节描述工作流；第 6 节讨论模型检查在流程中的角色、结论的边界与适用范围。附录说明工具的使用方式。

2 最小示例：过期回调

2.1 模型

模型不模拟程序的每一行，只保留影响“提交是否合法”的状态：资源当前的 incarnation、每个操作启动时绑定的 incarnation、操作所处的阶段，以及资源上最后一次写入来自哪一代的操作。

---------------------------- MODULE StaleCallback ----------------------------
EXTENDS Naturals

CONSTANTS Ops,             \* 可能并发的异步操作
          MaxIncarnation,  \* worker-A 最多被重建到第几代
          CheckIncarnation \* Commit 是否校验 incarnation

VARIABLES incarnation,  \* worker-A 当前是第几代实体
          opPhase,      \* 每个操作所处阶段
          opBinding,    \* 每个操作启动时绑定的 incarnation
          lastWriter    \* 当前资源上最后一次写入来自哪一代的操作，0 表示尚无写入

vars == <<incarnation, opPhase, opBinding, lastWriter>>

TypeOK ==
  /\ incarnation \in 1..MaxIncarnation
  /\ opPhase \in [Ops -> {"idle", "running", "done", "committed", "discarded"}]
  /\ opBinding \in [Ops -> 0..MaxIncarnation]
  /\ lastWriter \in 0..MaxIncarnation

Init ==
  /\ incarnation = 1
  /\ opPhase = [o \in Ops |-> "idle"]
  /\ opBinding = [o \in Ops |-> 0]
  /\ lastWriter = 0

StartOp(o) ==            \* 操作启动，记下此刻的 incarnation
  /\ opPhase[o] = "idle"
  /\ opPhase' = [opPhase EXCEPT ![o] = "running"]
  /\ opBinding' = [opBinding EXCEPT ![o] = incarnation]
  /\ UNCHANGED <<incarnation, lastWriter>>

Replace ==               \* 删除并重建 worker-A：名字不变，换一代实体
  /\ incarnation < MaxIncarnation
  /\ incarnation' = incarnation + 1
  /\ lastWriter' = 0
  /\ UNCHANGED <<opPhase, opBinding>>

Complete(o) ==           \* 异步结果返回
  /\ opPhase[o] = "running"
  /\ opPhase' = [opPhase EXCEPT ![o] = "done"]
  /\ UNCHANGED <<incarnation, opBinding, lastWriter>>

Commit(o) ==             \* 把结果写入当前叫 worker-A 的资源
  /\ opPhase[o] = "done"
  /\ CheckIncarnation => opBinding[o] = incarnation
  /\ opPhase' = [opPhase EXCEPT ![o] = "committed"]
  /\ lastWriter' = opBinding[o]
  /\ UNCHANGED <<incarnation, opBinding>>

Discard(o) ==            \* 丢弃已经过期的结果
  /\ opPhase[o] = "done"
  /\ opBinding[o] # incarnation
  /\ opPhase' = [opPhase EXCEPT ![o] = "discarded"]
  /\ UNCHANGED <<incarnation, opBinding, lastWriter>>

Next ==
  \/ Replace
  \/ \E o \in Ops : StartOp(o) \/ Complete(o) \/ Commit(o) \/ Discard(o)

Spec == Init /\ [][Next]_vars

\* 资源上的最后一次写入，只能来自绑定当前 incarnation 的操作
NoStaleWrite == lastWriter \in {0, incarnation}
=============================================================================

模型中没有出现名称 worker-A。名称在整个过程中不变，因此“只比较名称”的提交逻辑在模型中等价于不做任何比较，对应 CheckIncarnation = FALSE。Replace 将 lastWriter 置为 0，表示新一代资源上尚无写入。Ops 包含两个操作，使 TLC 同时探索操作之间的交错。

操作被拆分为 StartOp、Complete 与 Commit 三个动作，因为缺陷只在“绑定 incarnation”与“提交”之间插入 Replace 时出现；若把操作建模为单一原子动作，该交错在模型中不可表达。模型粒度因此由待检查的性质决定，而不是由源代码的结构决定。

待检查的性质 NoStaleWrite 是状态不变量：任意时刻，资源上的最后一次写入要么不存在，要么来自绑定当前 incarnation 的操作。“每次提交都必须获得授权”属于动作性质，在 TLA+ 中应写作 [][\A o \in Ops : Commit(o) => opBinding[o] = incarnation]_vars，而不能把动作直接置于 □ 之下。在本模型中，两种表述约束的是同一要求；采用状态不变量，便于直接作为 tla-check 的预期结果 invariant:NoStaleWrite。

2.2 反例

对应缺陷实现的配置如下：

CONSTANTS
  Ops = {o1, o2}
  MaxIncarnation = 2
  CheckIncarnation = FALSE
SPECIFICATION Spec
INVARIANTS TypeOK NoStaleWrite
CHECK_DEADLOCK FALSE

所有操作结束、incarnation 达到上限后，模型没有后继状态。这是有限配置的自然终点，不代表系统死锁，因此关闭死锁检查。

TLC 在 28 个不同状态内找到违例，给出一条 5 步轨迹。以下摘自实际输出，省略了源码位置以及在整条轨迹中始终处于 idle 的 o2：

Error: Invariant NoStaleWrite is violated.
State 1: <Initial predicate>
/\ incarnation = 1  /\ lastWriter = 0  /\ opBinding = (o1 :> 0)  /\ opPhase = (o1 :> "idle")
State 2: <StartOp(o1)>
/\ incarnation = 1  /\ lastWriter = 0  /\ opBinding = (o1 :> 1)  /\ opPhase = (o1 :> "running")
State 3: <Replace>
/\ incarnation = 2  /\ lastWriter = 0  /\ opBinding = (o1 :> 1)  /\ opPhase = (o1 :> "running")
State 4: <Complete(o1)>
/\ incarnation = 2  /\ lastWriter = 0  /\ opBinding = (o1 :> 1)  /\ opPhase = (o1 :> "done")
State 5: <Commit(o1)>
/\ incarnation = 2  /\ lastWriter = 1  /\ opBinding = (o1 :> 1)  /\ opPhase = (o1 :> "committed")

该轨迹与图 1 的四个事件一一对应：o1 在第 1 代启动，资源被替换为第 2 代，o1 的结果返回并被提交，最终 lastWriter = 1 而 incarnation = 2。

2.3 修复与配置

修复为 Commit 中的守卫：仅当操作绑定的 incarnation 等于当前 incarnation 时允许提交，过期结果经 Discard 丢弃。为使修复前后共用同一模型，守卫是否生效由常量 CheckIncarnation 控制。表 1 列出三个配置的检查结果，每个配置的检查耗时均在 1 秒以内。

表 1：StaleCallback 各配置的检查结果。

配置 MaxIncarnation CheckIncarnation 预期 结果 不同状态数
Buggy.cfg 2 FALSE invariant:NoStaleWrite 违例，5 步反例 28
Fixed.cfg 3 TRUE success 通过 224
Vacuous.cfg 1 FALSE success 通过 16

Fixed.cfg 是修复后的回归检查。Buggy.cfg 在修复后仍需保留：它不再描述当前实现，而是作为负向见证，证明模型能够表达并捕获目标错误。此后每次修改模型，两者都应重新执行，前者必须通过，后者必须以 NoStaleWrite 违例结束。模型与三个配置文件可直接下载运行：StaleCallback.tla、Buggy.cfg、Fixed.cfg、Vacuous.cfg。

3 判别性与负向见证

表 1 中的 Vacuous.cfg 使用缺陷实现，却通过了检查。原因在于 MaxIncarnation = 1 时 Replace 不可能发生，过期结果不存在，NoStaleWrite 也就不可能被违反。这一通过结果不支持任何关于提交逻辑的结论。

model-with-tla 将这一性质称为模型的判别性（discriminability）：模型不仅要允许正确行为，还必须能够表达并到达目标错误。对每条重要的 Safety 性质，工作流要求提供一个负向见证（negative witness），即一个预期以该性质违例结束的配置，以确认检查确实能够区分正确与错误的行为。

当模型由 Agent 编写时，负向见证还承担另一项职能：防止模型被修改到恰好通过。在不改动缺陷提交逻辑的前提下，至少有三种修改可以使 StaleCallback 通过检查：

  • 缩小常量，如令 MaxIncarnation = 1；
  • 削弱性质，如将 NoStaleWrite 改为 lastWriter <= incarnation，旧结果写入新资源时 1 <= 2 仍然成立；
  • 为环境动作添加过强的守卫，如要求 Replace 只能在没有进行中操作时发生（41 个不同状态，通过）。产品无法阻止资源在操作进行期间被删除，该守卫实际上是把缺陷假设掉了。

三种修改都会使 Buggy.cfg 不再违例：以 --expect invariant:NoStaleWrite 执行时，tla-check 报告观察结果为 success，与预期不符，并以退出码 4 结束。需要说明，以上三种修改是为演示而构造的；在笔者回顾的使用记录中，并未观察到 Agent 为通过检查而如此修改模型。

使用记录中实际出现的，是无意写出的空洞模型。在一个委托授权网关的模型中，Agent 写下了如下动作子句：

/\ startedWithAuthority' = startedWithAuthority /\ active /\ approved = payload

其意图是把三个条件的合取赋给 startedWithAuthority'。但 TLA+ 中 = 的优先级高于 /\，该子句实际被解析为 (startedWithAuthority' = startedWithAuthority) /\ active /\ (approved = payload)：变量保持原值，后两项成为动作的守卫。startedWithAuthority 因而永远不会变为假，授权性质 AuthorizedEffect 也就不可能被违反。正向配置照常通过；暴露问题的是负向配置，它们预期违例，实际却通过，tla-check 报告不匹配。补上括号后，负向配置按预期失败。同类错误在同一工作过程中的另一个模型里再次出现，同样由负向配置检出。

负向见证有其边界：它只能确认已预见的错误类别可以被捕获，不能发现模型中根本没有表达的状态或动作。模型遗漏了什么，仍需通过需求核对与人工审查来判断。

4 案例研究

本节的两个案例取自笔者在实际项目中的使用记录。第一个是设计阶段的建模，第二个是故障后的诊断。

4.1 认领协议的设计期建模

kinmesh2 是一个由 agent 处理团队消息的协作系统。消息进入收件箱后，worker 认领一条投递（delivery），将其派发至执行端，并观察执行端上的运行是否结束。系统计划引入运行槽位：每个 agent 的并发运行数有上限，停滞的运行须让出槽位，同一任务同一时刻至多一个运行。实现之前，Agent 先对该认领协议建模。

模型（416 行）覆盖了两个 worker 之间的租约竞争、worker 停滞或崩溃后携带过期状态恢复、执行端上的运行可能永不结束，以及人工的停止等待、取消与恢复操作。模型声明 6 条 Safety 性质和 2 条 Liveness 性质，并为其中 7 条各提供一个负向变体。检查规模为 2 个 agent、2 个 worker、4 条投递。这一过程有四项结果。

反例的分诊。 第一个反例违反 Liveness 性质 QueuedDispatches，其成因在模型而不在设计：模型允许一个正常运行的 worker 在下一步之前失去租约，而产品的时限设定排除了这种情况。修正环境假设后，第二个反例违反不变量 Settled：投递被人工取消时，没有任何规则要求持有其派发租约的 worker 释放租约。这是协议设计中的真实缺口，随后被列为实现必须满足的要求。可见，反例在作为设计缺陷处理之前需要先分诊：它可能指向设计，也可能只说明模型对环境的描述有误。

空洞的负向变体。 负向变体 GiveWayFreesTask（让出槽位时一并释放任务锁）应当违反“同一任务至多一个运行”，但在 1700 万个状态内没有失败。原因是积压上限 BacklogCap 被设为 1：第一个运行让出槽位后积压即达上限，派发随之暂停，同一任务的第二个运行无从产生，任务规则从未生效。也就是说，正向检查对该性质的通过是空洞的，与第 3 节的 Vacuous.cfg 属于同一类问题。上限改为 2 后，该变体在 3 秒内失败；新增的上限为 2 的 Safety 配置在 3.14 亿个状态上通过。

状态空间规模。 含 Liveness 的完整检查以单线程执行，8 小时内未能完成。状态规模主要来自 2 个 agent 与 2 个 worker 之间的交错，而非某个单独的动作。精简模型（去除不影响任何性质的状态与动作，并限制人工操作次数）后，4 条投递的 Safety 检查以 8 线程在 33 分钟内完成，共 8500 万个状态；Liveness 检查的推进速度约为每分钟 6 万个状态，估计需一天以上。最终结论按实际覆盖范围记录：4 条投递的 Safety 性质已验证；7 个负向变体均在精简前的模型上确认违例；精简后模型的 Liveness 性质未验证。模型检查随之由验收条件改为建议性检查。

模型与实现的对照。 模型将“已派发”定义为一个显式的状态谓词：启动记录已写入。实现中没有对应的状态字段，该条件由其他字段间接推断。两者的语义差异构成了一个实际缺陷：实现以“启动参数已生成”近似“可能已在执行端运行”，而启动参数在调用执行端之前即已写入，因此一条从未发出、又被退回队列的投递永远不会满足过期条件。修复引入了与模型一致的显式状态：worker 在调用执行端之前，在自身租约下将投递标记为 uncertain；若租约已失效，则不调用执行端3。该缺陷不是由 TLC 反例给出的，而是在为模型状态寻找实现对应物时发现的。

在这一案例中，设计缺口、空洞变体与实现缺陷都出现在建模和早期检查阶段；此后耗时最长的 Liveness 检查没有产生新的反例。这说明检查规模、时间预算以及哪些检查构成验收条件，应在建模开始时确定。

4.2 外部副作用的取消责任

第二个案例来自一个管理临时远程开发环境的控制面：关闭环境时，需要取消代码托管平台上正在运行的 CI 任务。在一次平台局部故障中，查询任务状态的请求失败；此时关闭已被记录，取消请求却未发出，任务持续运行。

最初的修复只移除了失败的状态查询。随后的建模表明，原模型把关闭视为单一步骤。将其拆分为“记录关闭意图”“发出取消”与“平台确认取消”三步后，模型暴露出一个中间状态：关闭一经记录，重复的关闭请求便不再具有发出取消的权限，取消责任在该状态下丢失。最终的修复把待取消状态持久化，仅在平台接受取消后才清除，并以不变量 CancelResponsibilityRetained 加以检查。模型没有发现这次故障，但它把修复范围从移除一次查询，扩展为在中间状态中保留取消责任。

该案例说明，提交权限与清理责任可以分离：一个操作可能已无权修改当前状态，却仍需为其造成的外部效果负责。对应地，模型需要显式表达效果归属（effect ownership）、取消能够撤回与不能撤回的内容，以及系统在有限步内到达稳定终态的收敛（convergence）要求。

5 工作流

上述过程中的建模、配置、反例解读与负向见证设计均由 Agent 完成初稿。model-with-tla 的作用是将这些步骤组织为可重复的工作流：Skill 规定何时值得建模、如何划定模型边界与定义性质、各类任务可修改的文件范围；TLC 负责穷举；tla-check 以固定版本的工具链执行 SANY 与 TLC，比较预期结果与实际观察，并输出结构化证据（图 3）。

图 3：model-with-tla 工作流：需求、模型检查、实现映射与验证证据。

以需求而非实现为起点。 当前实现可能正是错误的来源。把实现直接翻译为 TLA+，检查通过也只能说明模型满足它自身声明的性质。在第 2 节的例子中，若照实现只建模名称，NoStaleWrite 根本无法表述。因此，工作流要求分别记录产品需求与已确认的设计决策、当前实现的行为、外部系统提供的保证，以及尚未证实的假设。例如，外部 API 调用超时并不证明操作未执行；若业务要求避免重复副作用，模型必须保留“操作已生效而响应丢失”的可能，除非外部契约明确排除这种情况（图 4）。

图 4：一次带外部副作用的调用中的三个边界：外部接受请求、响应送达与本地提交。超时分支表示结果未知，而非外部操作未发生。

从反例到测试。 TLC 的反例是抽象的状态轨迹，需要映射到领域事件与实现中的关键边界，再构造为可重复执行的受控测试（图 5）。对第 2 节的轨迹，对应的测试在回调处暂停操作（State 2），删除并重建资源（State 3），放行回调（State 4、5），最后断言第 2 代资源未被旧结果修改。

图 5：反例到受控测试的语义映射。该映射不构成模型结果对实现正确性的证明。

证据分层与结论状态。 模型通过不等于实现通过：模型可能把一段行为视为原子操作，而实现允许在其中插入其他任务；模型区分了 incarnation，实现却可能仍以可复用的名称作为身份。工作流因此分别收集各层证据，并核对其身份、操作与终态语义是否一致（图 6）。证据不完整时，结论按表 2 的状态标注，而不笼统地报告为“已验证”。

图 6：需要相互对应的证据来源。单一层次的通过结果不能逐层推出其他层次的结论。

表 2：结论状态。

状态 含义
closed 结论所需的每一层证据均已具备，且语义一致
scoped 内部行为有证据支持，但平台、兼容性或时序方面的结论仅在记录的环境中成立
drifted 证据曾经一致，但模型、实现、工具链或外部环境此后发生了变化
blocked 某一前提缺失，证据无法收集；这既不表示通过，也不表示失败
unproved 关键证据层缺失、相互矛盾、空洞（如 Vacuous.cfg），或依赖未经证实的假设

检查结果的判定。 tla-check 比较的是预期结果与观察结果，而不仅是进程退出状态。若负向配置预期 NoStaleWrite 违例，而 TLC 首先报告 TypeOK 违例，说明模型在到达目标错误之前已出现其他问题，该结果不被视为重现了目标错误。工具同时校验 TLA+ 工具链的版本与校验和，将 TLC 的临时状态隔离在代码库之外，并报告状态数、搜索深度与耗时。这些机制不判断抽象是否正确，但减少了工具调用、版本漂移与结果解读方面的不确定性。

工作流分为五种模式：design 用于在实现前建立需求模型；diagnose 用于把已观察到的故障构造为可复现的反例，不修改产品代码；refine 用于对齐模型与实现并补充受控测试；review 与 verify 为只读模式，分别用于审查语义缺口和重新执行已有检查、发现漂移。

6 讨论

6.1 模型检查在流程中的角色

对使用记录的回顾显示，TLC 很少是缺陷的首个发现者。多数违例来自有意构造的负向配置，或是先由测试、代码审查复现，再写入模型的问题。发现多发生在建模过程中：为写出模型，Agent 必须精确定义状态谓词，再以这些定义对照实现，第 4.1 节的“已派发”即为一例。由反例直接揭示设计缺口的情形（如 Settled）相对少见。

TLC 的主要贡献在修复之后。测试复现一条违例顺序，修复后该顺序通过，只能说明这一顺序不再出错。TLC 对修复后的模型做穷举检查，说明在给定的有限配置内，没有任何事件交错会违反该性质；负向配置则确认这一结论不是空洞的。在第 4.2 节中，测试检查的是若干条显式构造的顺序，而 CancelResponsibilityRetained 在模型的全部可达状态上成立；在第 4.1 节中，Safety 检查覆盖了 4 条投递下的 8500 万个状态。

因此，在本文所述的流程中，建模首先是一种迫使定义精确化的设计审查，承担发现问题的职能；TLC 则在修复之后，就“这一类问题已被消除”给出有明确范围的完备性结论。

6.2 结论的边界

即使检查结果不是空洞的，其适用范围也有三方面的限制。

其一，TLC 只检查给定的模型与配置。模型遗漏的状态、被配置排除的路径，都不在结论覆盖之内。

其二，Safety 与 Liveness 依赖不同的前提。Safety 断言坏事不会发生；Liveness 断言在给定假设下，好事终将发生。例如，对 Complete 施加弱公平（weak fairness），模型中的响应便终将到达；但这等于假设外部服务终将响应。这是一条需要单独声明的环境假设，而不是 TLC 验证得到的结论。

其三，模型与实现之间的对应关系需要单独验证。有限模型检查、受控测试与真实平台观测是不同层次的证据，不能相互替代。工作流中的 model adequacy（模型是否足以支撑结论）、refinement（低层模型或实现是否遵从高层模型）与 evidence closure（表 2 的状态标注）用于在自动化过程中保持这些边界；它们提高了结论的可审查性，但不能消除模型错误、需求不完整或外部系统违反假设的风险。

6.3 成本与适用范围

检查成本取决于相互交错的参与者数量，而非模型的行数。第 2 节的模型 60 余行，各配置在 1 秒内完成；第 4.1 节的模型 416 行，含 Liveness 的完整检查在 8 小时内未能完成。无论规模如何，最需要人工判断的环节都是：决定模型保留哪些状态，确认负向见证成立，以及为检查设定预算。这些环节可以由 Agent 起草，但也正是 Agent 最容易出错的地方。

纯展示性的界面、静态内容或没有复杂生命周期的确定性操作，通常以测试与代码审查即可覆盖。模型检查适用于涉及并发请求、异步回调、资源替换、重试与去重、取消后的副作用、事务中间状态、超时恢复或进展要求的系统，尤其是正常路径易于实现、而异常路径会改变资源身份、操作权限或副作用责任的功能。

7 结论

Coding Agent 提高了实现速度，却并不因此加深对并发行为与生命周期边界的理解。本文描述的工作流在 Agent 辅助编程中增加了一条独立于测试的反馈路径：从需求出发写出可检查的状态机，由建模过程暴露定义上的缺口，由 TLC 在修复前给出反例、在修复后给出有限配置内的穷举结论，并以负向见证确认这一结论不是空洞的，再通过受控测试与外部证据核对实现。它的目标不是为代码提供完整的形式化证明，而是把原本停留在直觉中的时序假设，转化为可以表达、检查、反驳与回归验证的工程对象。

Skill 随 ronhuafeng-engineering 插件发布。Claude Code 中的安装命令：

/plugin marketplace add ronhuafeng/skills-release
/plugin install ronhuafeng-engineering@ronhuafeng-skills

Codex CLI 中的安装命令：

codex plugin marketplace add ronhuafeng/skills-release --ref main
codex plugin add ronhuafeng-engineering@ronhuafeng-skills

运行环境需要 Java 11 或更高版本及 uv；TLA+ 工具链与 tla-check 已随 Skill 分发。该 Skill 设置了 disable-model-invocation，需要由用户显式调用并指定模式。第 6.3 节建议在调用时同时给出检查规模、时间预算与验收范围，例如：

/ronhuafeng-engineering:model-with-tla design 为收件箱的认领协议建模。Safety 检查使用 2 个 worker、3 条投递，单次不超过 10 分钟；每条 Safety 性质配一个负向配置；Liveness 检查仅作参考，不作为验收条件。

以第 2 节的模型为例，执行负向配置的命令如下（Fixed.cfg 将预期改为 success）：

"<skill-directory>/.tools/tla-check" check \
  --module "$PWD/StaleCallback.tla" \
  --config "$PWD/Buggy.cfg" \
  --expect invariant:NoStaleWrite
