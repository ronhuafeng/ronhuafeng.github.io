Agent 辅助编程中的 TLA+：如何判断模型真的检验了问题

一份关于 Coding Agent、TLA+ 与模型判别性的工程经验报告。本文以过期回调的可复现模型说明正向检查为何可能空洞，通过负向见证检出 Agent 编写的模型错误，并以十项仓库提交佐证的发现讨论建模、TLC 和实现对照各自提供的证据。

1 为什么模型检查通过还不够

一个异步操作针对名为 worker-A 的资源启动。它尚未完成时，资源被删除，又以相同名称重建。旧操作随后返回；如果提交逻辑只核对名称，旧结果就可能写入新资源（图 1）。顺序执行每一步都可能合理，错误却出现在步骤的交错中。

图 1：旧操作的回调在资源重建后到达，并错误地写入新资源。

这里的关键不是名称，而是身份。同名资源在不同时刻可以是不同的实体；本文将资源的每一代称为一个 incarnation。操作启动时绑定第 1 代，提交时资源已变为第 2 代，原有授权不能自动延续。要检验这个错误，模型至少需要区分两代资源，并允许“启动—替换—完成—提交”的顺序。

TLA+ 可以把状态、状态转换和不能出现的状态写成规约，由 TLC 在有限配置内枚举可达状态12。但检查器回答的是“这个模型在这个配置下是否违反所写的性质”，而不是“程序是否正确”。如果模型没有表达资源换代、配置排除了替换，或者性质被写得过弱，TLC 即使穷举所有可达状态，也可能得到一个与实际风险无关的通过结果。

图 2：测试执行选定的事件顺序；TLC 穷举有限模型的可达状态。示意图不表示实际覆盖率。

当 Coding Agent 参与编写规约时，问题还多了一层：Agent 能生成可以被工具解析、也能通过检查的模型，但这不等于它准确抓住了需求中的风险。本文关注的是如何让检查结果具有可解释的证据价值，而不只是获得一个 success。

实践中需要回答三个不同的问题：

  1. 模型有判别力吗？ 它能否表达并到达我们知道应该禁止的行为？
  2. 检查具体证实了什么？ TLC 在哪些状态空间、环境假设和时间预算内得出了结果？
  3. 模型对应实现吗？ 模型中的身份、原子边界和外部副作用，是否与代码实际允许的行为一致？

下面先给出可运行的最小模型，再讨论负向见证（negative witness）如何检测空洞模型。之后分析 2026 年 7—11 月 Coding Agent 使用记录中十项有仓库提交佐证的发现。作者同时是所用 Agent Skill model-with-tla 的作者3；本文报告观察与局限，不把这些案例当作方法优越性的对照实验。

2 最小实验：过期回调如何逃过检查

2.1 保留决定提交是否合法的状态

模型不复刻业务代码，只保留四类状态：资源当前的 incarnation、每个操作启动时绑定的 incarnation、操作阶段，以及最后一次写入来自哪一代。Ops 有两个操作，允许 TLC 探索它们与资源替换之间的交错。

---------------------------- MODULE StaleCallback ----------------------------
EXTENDS Naturals

CONSTANTS Ops,             \* 可能并发的异步操作
          MaxIncarnation,  \* worker-A 最多被重建到第几代
          CheckIncarnation \* Commit 是否校验 incarnation

VARIABLES incarnation,  \* worker-A 当前是第几代实体
          opPhase,      \* 每个操作所处阶段
          opBinding,    \* 每个操作启动时绑定的 incarnation
          lastWriter    \* 当前资源上最后一次写入来自哪一代的操作，0 表示尚无写入

vars == <<incarnation, opPhase, opBinding, lastWriter>>

TypeOK ==
  /\ incarnation \in 1..MaxIncarnation
  /\ opPhase \in [Ops -> {"idle", "running", "done", "committed", "discarded"}]
  /\ opBinding \in [Ops -> 0..MaxIncarnation]
  /\ lastWriter \in 0..MaxIncarnation

Init ==
  /\ incarnation = 1
  /\ opPhase = [o \in Ops |-> "idle"]
  /\ opBinding = [o \in Ops |-> 0]
  /\ lastWriter = 0

StartOp(o) ==            \* 操作启动，记下此刻的 incarnation
  /\ opPhase[o] = "idle"
  /\ opPhase' = [opPhase EXCEPT ![o] = "running"]
  /\ opBinding' = [opBinding EXCEPT ![o] = incarnation]
  /\ UNCHANGED <<incarnation, lastWriter>>

Replace ==               \* 删除并重建 worker-A：名字不变，换一代实体
  /\ incarnation < MaxIncarnation
  /\ incarnation' = incarnation + 1
  /\ lastWriter' = 0
  /\ UNCHANGED <<opPhase, opBinding>>

Complete(o) ==           \* 异步结果返回
  /\ opPhase[o] = "running"
  /\ opPhase' = [opPhase EXCEPT ![o] = "done"]
  /\ UNCHANGED <<incarnation, opBinding, lastWriter>>

Commit(o) ==             \* 把结果写入当前叫 worker-A 的资源
  /\ opPhase[o] = "done"
  /\ CheckIncarnation => opBinding[o] = incarnation
  /\ opPhase' = [opPhase EXCEPT ![o] = "committed"]
  /\ lastWriter' = opBinding[o]
  /\ UNCHANGED <<incarnation, opBinding>>

Discard(o) ==            \* 丢弃已经过期的结果
  /\ opPhase[o] = "done"
  /\ opBinding[o] # incarnation
  /\ opPhase' = [opPhase EXCEPT ![o] = "discarded"]
  /\ UNCHANGED <<incarnation, opBinding, lastWriter>>

Next ==
  \/ Replace
  \/ \E o \in Ops : StartOp(o) \/ Complete(o) \/ Commit(o) \/ Discard(o)

Spec == Init /\ [][Next]_vars

\* 资源上的最后一次写入，只能来自绑定当前 incarnation 的操作
NoStaleWrite == lastWriter \in {0, incarnation}
=============================================================================

名称 worker-A 不在模型中变化。因此，在这个抽象层次上，“只检查名称”相当于没有检查资源代际，即 CheckIncarnation = FALSE。Replace 把 lastWriter 清零，表示新一代资源尚未被写入。StartOp、Complete 和 Commit 必须分开：若将一次异步调用看成不可分割的动作，替换就无法插入绑定与提交之间，目标缺陷会被模型结构排除。

NoStaleWrite 是状态不变量：最后一次写入要么不存在，要么来自当前 incarnation。它与“每次提交都不能使用过期绑定”在这个模型中具有相同的违例判据：Commit 写入绑定代际，Replace 清空最后写入标记，其他动作不改变该标记。因此用不变量即可捕获过期提交，不必把源代码的每一步都带入规约。

2.2 从反例中读取错误顺序

缺陷配置保留资源替换，但关闭提交时的代际校验：

CONSTANTS
  Ops = {o1, o2}
  MaxIncarnation = 2
  CheckIncarnation = FALSE
SPECIFICATION Spec
INVARIANTS TypeOK NoStaleWrite
CHECK_DEADLOCK FALSE

TLC 在该配置下发现 NoStaleWrite 违例。下面是实际输出的精简摘录；省略源码位置和整个轨迹中始终为 idle 的 o2：

Error: Invariant NoStaleWrite is violated.
State 1: <Initial predicate>
/\ incarnation = 1  /\ lastWriter = 0  /\ opBinding = (o1 :> 0)  /\ opPhase = (o1 :> "idle")
State 2: <StartOp(o1)>
/\ incarnation = 1  /\ lastWriter = 0  /\ opBinding = (o1 :> 1)  /\ opPhase = (o1 :> "running")
State 3: <Replace>
/\ incarnation = 2  /\ lastWriter = 0  /\ opBinding = (o1 :> 1)  /\ opPhase = (o1 :> "running")
State 4: <Complete(o1)>
/\ incarnation = 2  /\ lastWriter = 0  /\ opBinding = (o1 :> 1)  /\ opPhase = (o1 :> "done")
State 5: <Commit(o1)>
/\ incarnation = 2  /\ lastWriter = 1  /\ opBinding = (o1 :> 1)  /\ opPhase = (o1 :> "committed")

轨迹包含 5 个状态、4 次状态转换：o1 绑定第 1 代，Replace 创建第 2 代，Complete 返回旧结果，Commit 将第 1 代的结果写入当前资源。初始状态不是一次转换，因此不把“5 个状态”写成“5 步操作”。这一反例说明缺陷配置确实能够到达目标错误。

2.3 同样的通过结果，可能有相反的含义

修复是在 Commit 中检查 opBinding[o] = incarnation，并通过 Discard 丢弃过期结果。为了用同一份规约对照修复前后行为，CheckIncarnation 控制该守卫是否启用。表 1 的结果在 Apple Silicon Mac 上用 TLC 1.8.0 预发布版、单个 worker 得到；三个配置均在 1 秒内完成。

表 1：StaleCallback 各配置的检查结果。

Fixed.cfg 的通过结果表明：在其有限配置下，修复模型没有到达 NoStaleWrite 违例。Vacuous.cfg 也通过了，却仍使用 CheckIncarnation = FALSE。区别在于它设置了 MaxIncarnation = 1，资源无法替换，过期写入自然无法出现。两次“通过”在输出形式上相同，在证据意义上却不同。

Buggy.cfg 因而不应在修复后被删除。它是保留已知错误的负向见证：每次改动规约时，修复配置应通过，缺陷配置应当准确违反 NoStaleWrite。模型和三个配置文件可直接运行：StaleCallback.tla、Buggy.cfg、Fixed.cfg、Vacuous.cfg。

3 负向见证：检查模型能否识别已知错误

3.1 判别性不是检查器的附加保证

本文把模型的判别性（discriminability）定义为：对于某条待检查的性质，在指定的负向配置中，模型能够表达并到达一个预期违反该性质的行为。正向配置检查“没有发现坏状态”；负向配置检查“已知坏状态是否还找得到”。两者相互补充，但任何一方都不能取代另一方。

这一做法与模型检查中的 vacuity 检测有关45，也借用了变异分析的思路：保留一个已知错误，确认验证机制能够使它失败6。它不是声称已经覆盖所有错误，而是针对一个明确的错误类别检验模型是否还有识别能力。类似地，LLM 生成后置条件的研究也以区分有缺陷程序的能力评价规约7。

以第 2 节的模型为例，下面三种操作都可能让一个仍允许过期提交的模型通过检查：

  • 将 MaxIncarnation 缩为 1，让 Replace 永远不能发生；
  • 把 NoStaleWrite 弱化为 lastWriter <= incarnation，使第 1 代写入第 2 代不再违例；
  • 给 Replace 加上“没有正在运行的操作才能替换”的守卫，排除产品原本允许的并发情形。

这些是为说明机制而构造的修改，不是观察到 Agent 为了通过检查而故意作弊的证据。对目标负向配置，它们都会使预期的 NoStaleWrite 违例消失；tla-check 因此将“预期违例、实际通过”报告为不匹配，并以退出码 4 结束。第三种修改对应的演示配置访问了 41 个不同状态。错误不是检查器漏报，而是待检查的行为已被规约或配置排除。

3.2 实际案例 F7：一个括号错误制造了空洞模型

使用记录中，Agent 的确写出过无意的空洞模型。一个委托授权网关模型包含如下动作子句：

/\ startedWithAuthority' = startedWithAuthority /\ active /\ approved = payload

Agent 想表达的是把三个条件的合取赋给 startedWithAuthority'。但在 TLA+ 中，= 的优先级高于 /\，实际解析为 (startedWithAuthority' = startedWithAuthority) /\ active /\ (approved = payload)。也就是说，第一个条件要求变量保持不变，后两个条件成为动作的守卫；代码并没有按预期更新授权状态。

在该模型的初始条件和转换关系下，startedWithAuthority 无法变为假，于是授权性质 AuthorizedEffect 不能以预期方式被违反。正向配置继续通过。异常信号来自负向配置：它们本应产生指定性质的违例，却得到 success。排查并补上括号后，负向配置重新按预期报错。同类问题在同一工作过程的另一模型中再次出现，也由负向配置检出；表 2 将这两次记作同一类发现 F7，而非两个独立项目。

这个案例比人为缩小 MaxIncarnation 更能说明 Agent 场景的风险：形式化语言的语法合法，工具也如实检查了模型，但 Agent 以为自己写下的状态转换与实际解析结果不同。负向见证提供了一个反馈信号，迫使编写者重新检查模型的语义。

3.3 负向见证能证实什么，不能证实什么

负向见证只能支持一个有限结论：对于预先指定的错误类别和配置，当前模型没有把它排除或掩盖。 它不能证明性质完整，不能保证模型包含了所有重要动作，更不能单独证明实现正确。一个模型即使通过正、负向检查，仍可能遗漏真实系统的某个中间状态。

因此，负向见证应当与需求核对、环境假设审查和模型—实现对照一起使用，而不是被当作模型正确性的证书。

“首先发现”是一种记录分类，不是独立贡献的因果分解。为写出可检查的模型而精确定义状态，本身可能受到之后必须通过 TLC 的约束；反例检查也可能引导下一轮建模。没有等投入的代码审查或无 TLC 建模对照，就无法估计哪种活动单独创造了多少价值。以下两个场景展示的，是这些活动如何相互作用，而非胜负排名。

5 详细案例：设计缺口与外部副作用

5.1 认领协议：反例、空洞配置与实现语义（F1–F3）

项目 A 是一个由 Agent 处理团队消息的协作系统8。worker 认领投递（delivery），将其派发到执行端，并等待运行结束。系统计划增加运行槽位限制：每个 agent 的并发运行数有上限，停滞的运行要让出槽位，同一任务同一时刻最多只有一个运行。实现之前，Agent 对认领协议进行了建模。

模型共有 416 行，包含两个 worker 的租约竞争、携带过期状态的恢复、可能永不结束的外部运行，以及人工停止等待、取消和恢复等操作；声明 6 条 Safety 性质和 2 条 Liveness 性质，为其中 7 条准备了负向变体。主配置为 2 个 agent、2 个 worker、4 条投递。检查在一台 10 核 Apple Silicon Mac 上使用 TLC 1.8.0 预发布版，JVM 堆为 7.3 GB；不同配置的实际结果见表 3。

表 3：项目 A 认领协议模型的检查记录。“精简”指去除了不影响任何性质的状态与动作，并限制了人工操作次数的版本；“—”表示会话记录中未注明。

F1：先分诊反例，再判断设计。 TLC 首先报告了 QueuedDispatches 的 Liveness 反例，但这是模型环境假设的问题：它允许正常运行的 worker 在下一步之前失去租约，而产品的时限设定排除了这种情况。修正假设后，另一个反例违反 Settled：投递被人工取消，却没有规则要求 worker 释放其派发租约。后一个反例对应真实的设计缺口，随后成为实现要求。反例本身不自动等于代码 Bug；首先要判断它是否来自产品允许的行为。

F3：负向配置没有失败，也是发现。 负向变体 GiveWayFreesTask 模拟“让出槽位时错误地释放任务锁”，预期违反“同一任务至多一个运行”。但在 BacklogCap = 1 的配置中，TLC 探索 1700 万个状态仍未找到违例。进一步分析发现，积压达到上限后派发暂停，第二个运行根本不会启动；配置把本应测试的行为排除了。将 BacklogCap 改为 2 后，3 秒内出现预期违例。这里不能把“1700 万状态未失败”直接当成安全证据，决定性信息来自对不可达原因的分析及修正后的负向检查。

F2：查找模型状态在代码中的对应物。 模型把“已派发”定义为启动记录已写入；实现却通过其他字段推断这一状态，并把“启动参数已生成”近似为“可能已在执行端运行”。启动参数实际在调用执行端前就已写入，导致一条从未发出的投递被退回队列后无法满足过期条件。修复引入显式的 uncertain 状态：worker 在自身租约下、调用执行端之前写入它；若租约已失效，就不再调用执行端9。这个问题没有由 TLC 反例直接提出，而是在寻找模型与实现状态的对应关系时暴露。

检查的成本与停止条件。 表 3 中，原始模型的完整 Safety + Liveness 检查在 8 小时内未完成；Safety 在 BacklogCap = 2 下检查 3.14 亿个状态后通过。精简模型的 Safety 检查在 BacklogCap = 1 下访问 8500 万个状态、耗时 33 分钟；Liveness 检查仍未完成。精简改变了模型行为，两个状态数不能直接用来比较效率。最终可报告的范围是：特定配置下 Safety 已检查，7 个负向变体在原始模型上确认了违例，精简模型没有重新运行全部负向变体，Liveness 未完成验证。项目也因此将模型检查从硬性验收条件改为建议性检查。

5.2 关闭操作：取消责任不能随状态消失（F4）

项目 B 的控制面负责管理临时远程开发环境。关闭环境时，还需要取消代码托管平台上仍在运行的 CI 任务。一次平台局部故障使“查询任务状态”失败：本地已记录关闭，取消请求却未发出，外部任务继续运行。

最初的修复只是移除那次易失败的查询。之后建模时，Agent 将原本单步的“关闭”拆成“记录关闭意图”“发出取消请求”“平台确认取消”。这个拆分显露了被原修复遗漏的中间状态：关闭意图一旦记录，重复关闭不再具备触发取消的权限，尚未完成的取消责任于是消失。

最终实现持久保存待取消状态，只有平台接受取消后才清除；模型以不变量 CancelResponsibilityRetained 检查这一要求。保留旧行为的负向配置违反不变量，修复模型在其有限配置的可达状态上满足它。此处，线上故障先于建模；建模并未“发现”原故障，却改变了修复范围，从绕过一次失败查询转为保证中间状态中责任不丢失。

F4 还揭示一种重要区分：操作失去修改当前资源的权限，不等于它造成的外部效果已被撤销。身份和提交授权、取消责任和最终收敛应分别建模；尤其在外部 API 超时后，不能把“没有收到响应”当成“平台没有执行”。

6 从检查输出到工程证据

6.1 三道不同的关口

以上案例可以组织成一个逐层检查的工作流，而不是“写模型—跑 TLC—宣布正确”的直线流程。

第一道关口是表达能力。从需求定义身份、状态与动作边界；对重要 Safety 性质配备能达到指定违例的负向见证。F3 和 F7 表明，工具运行成功不意味着这道关口已经通过。

第二道关口是有限模型检查。在明确的配置和环境假设下运行 TLC，区分预期性质违例、其他性质先行违例、检查成功、资源预算耗尽与未完成。负向结果必须命中指定性质，不能把任何报错都算成成功的负向见证。F1 的反例分诊说明，找到轨迹后仍需要判断环境假设是否符合产品。

第三道关口是实现对应。将模型的抽象状态、原子切分和反例轨迹对应到代码，必要时用可控的事件顺序写回归测试。F2 的问题恰恰出现于模型状态与实现字段无法一一对应的地方。模型通过并不自动把结果传递到实现；本文也没有做正式的 refinement 证明或生产轨迹校验。

三道关口不构成互相替代的证明链：前两道能提高模型检查结论的可解释性，第三道提供部分代码层面的证据，但仍不足以推出任意环境下实现正确。

6.2 Safety、Liveness 与环境假设不能混为一谈

Safety 关心坏状态是否可达，Liveness 关心系统能否持续取得进展。后者往往依赖公平性或外部服务最终响应的假设。例如，若假定 Complete 满足弱公平，模型可能据此得到“操作最终完成”的结论；这不是 TLC 证明了真实网络服务一定响应，而是模型把该条件作为前提。

同样，状态穷举只覆盖指定的有限配置。小范围假设认为许多缺陷能在小规模实例中暴露10，但这不意味着小配置的通过可以无条件推广到更大的系统。表 3 的结果应当连同参与者数量、配置常量、检查类型以及中止的任务一起阅读。

6.3 发现、确认与修复不应争夺同一个标签

十项发现里，TLC 不是最常见的第一条问题线索；它在反例确认、负向见证和修复后有限检查中发挥了不同作用。这既不支持“TLC 只是最后盖章”，也不支持“缺陷主要由 TLC 自动发现”。可观察到的工作方式更接近一个反馈循环：精确定义状态会推动审查，TLC 暴露某些错误或无效配置，开发者再修正规约或实现，随后重新检查。

把“第一次注意到问题”与“为修复提供何种证据”分开记录，比用单一发现数量评价形式化方法更有信息量。

6.4 成本、适用范围与停止条件

最小模型只有约 60 行，各配置不到 1 秒；认领协议模型 416 行，有些 Liveness 检查在数小时后仍未完成。运行成本主要取决于参与者、动作和状态的组合，而不是代码行数。本文没有可靠记录建模人工时间或 Agent 交互成本，不能据此估算投入产出比。

并发认领、资源替换、重试与去重、外部取消、超时恢复和跨步骤副作用，通常值得考虑这种建模方式；纯展示页面、静态内容或简单确定性操作，测试和代码审查往往更经济。开始建模时就应写明检查规模、时间预算、必须通过的 Safety 性质、负向见证以及 Liveness 能否作为验收条件。没有完成的检查应明确标为未完成，而不是归入通过。

7 与已有工作的关系

TLA+ 和 TLC 在工业界的应用已有成熟先例。AWS 的经验说明，设计阶段的形式化规约可以暴露分布式协议中的深层问题11。本文没有提出新的模型检查算法，讨论的是 Coding Agent 参与规约编写后，怎样判断检查结果与工程问题是否相干。

模型检查研究长期关注空洞满足（vacuity）：性质成立可能只是因为使其有意义的前提从未出现45。第 2 节的 Vacuous.cfg 和 F3 是配置使关键行为不可达的具体实例；负向见证则采用类似变异分析的办法，要求已知错误必须被目标性质检出6。这与后置条件研究所强调的 discriminative power 有相通之处7，但不能据此宣称二者是完全相同的评价指标。

另一条研究路线关注规约与程序的联系。MongoDB 的 eXtreme Modelling 使用程序轨迹对照 TLA+ 模型12；针对分布式程序的轨迹校验工作进一步研究了如何检查实现行为与规约的符合性13。本文案例仅将抽象反例映射为受控测试，没有进行这类轨迹验证，因而对实现所能提出的保证较弱。

已有研究也直接评估了 LLM 从自然语言生成 TLA+ 规约的语义正确性，并指出结果存在明显风险14。本文的场景不是一次生成即结束：Agent 可以在 TLC 与负向配置反馈下迭代修模。F7 表明，反馈机制有实际作用；同时，它也说明工具并不会自动替 Agent 理解规约语义。

8 证据局限

样本选择与利益相关。 数据只来自作者自己的项目；作者也是 model-with-tla 的开发者。筛选保留了有提交佐证的发现，但无法构成全部建模尝试的无偏样本，也不支持任何总体发现率。

分类误差与缺少对照。 首次发现途径依据会话可见记录判断，无法观察未记录的人工思考。两个 LLM agent 辅助分类，但没有第二名独立研究者复核；同时没有同等投入的普通代码审查或不使用 TLC 的建模组，不能据此估计因果效果。

复核范围不同。 项目 A 及其模型、修复提交可以公开查阅；项目 B、C、D 已匿名，读者无法独立核实。第 2 节的最小模型最容易复现，但它证明的是机制可行，不代表十项发现的普遍性。

配置与测量范围。 状态数和时间来自特定硬件上的运行，部分检查因预算中止。TLC 的通过只覆盖给定模型、配置和性质；受控测试只覆盖被执行的实现轨迹。两类证据都不能自动替代对真实环境行为的证明。

9 结论

在这些 Coding Agent 使用记录中，建模迫使开发者说明身份、授权与中间状态，TLC 提供反例、负向见证反馈以及指定配置下的穷举检查。重要的不是把缺陷发现归功于哪一个单独环节，而是让每一环节的证据回答它实际能回答的问题。

本文最直接的工程建议是：对重要性质，同时维护应当通过的配置和必须命中指定违例的负向配置。 正向结果说明有限模型中未发现错误；负向结果说明至少一个已知错误仍可被模型表达和识别。接着再用实现对照、受控测试与明确的环境假设限定结论范围。这样得到的不是“Agent 已证明程序正确”，而是一组可复查、能指出自身失效方式的工程证据。

附录 A：工作流

model-with-tla 把建模、配置、反例解读与负向见证设计组织为可重复的工作流：Skill 规定何时值得建模、如何划定模型边界与定义性质、各类任务可修改的文件范围；TLC 负责穷举；tla-check 以固定版本的工具链执行 SANY 与 TLC，比较预期结果与实际观察，并输出结构化证据（图 3）。

图 3：model-with-tla 工作流：需求、模型检查、实现映射与验证证据。

以需求而非实现为起点。 把实现直接翻译为 TLA+，检查通过也只能说明模型满足它自身声明的性质。在第 2 节的例子中，若照实现只建模名称，NoStaleWrite 根本无法表述。工作流因此要求分别记录产品需求与已确认的设计决策、当前实现的行为、外部系统提供的保证，以及尚未证实的假设。例如，外部 API 调用超时并不证明操作未执行；若业务要求避免重复副作用，模型必须保留“操作已生效而响应丢失”的可能，除非外部契约明确排除这种情况（图 4）。

图 4：一次带外部副作用的调用中的三个边界：外部接受请求、响应送达与本地提交。超时分支表示结果未知，而非外部操作未发生。

从反例到测试。 TLC 的反例是抽象的状态轨迹，需要映射到领域事件与实现中的关键边界，再构造为可重复执行的受控测试（图 5）。对第 2 节的轨迹，对应的测试在回调处暂停操作（State 2），删除并重建资源（State 3），放行回调（State 4、5），最后断言第 2 代资源未被旧结果修改。

图 5：反例到受控测试的语义映射。该映射不构成模型结果对实现正确性的证明。

证据分层与结论状态。 模型可能把一段行为视为原子操作，而实现允许在其中插入其他任务；模型区分了 incarnation，实现却可能仍以可复用的名称作为身份。工作流因此分别收集各层证据，并核对其身份、操作与终态语义是否一致（图 6）。证据不完整时，结论按表 A1 的状态标注，而不笼统地报告为“已验证”。

图 6：需要相互对应的证据来源。单一层次的通过结果不能逐层推出其他层次的结论。

表 A1：结论状态。

状态 含义
closed 结论所需的每一层证据均已具备，且语义一致
scoped 内部行为有证据支持，但平台、兼容性或时序方面的结论仅在记录的环境中成立
drifted 证据曾经一致，但模型、实现、工具链或外部环境此后发生了变化
blocked 某一前提缺失，证据无法收集；这既不表示通过，也不表示失败
unproved 关键证据层缺失、相互矛盾、空洞（如 Vacuous.cfg），或依赖未经证实的假设

检查结果的判定。 tla-check 比较的是预期结果与观察结果，而不仅是进程退出状态。若负向配置预期 NoStaleWrite 违例，而 TLC 首先报告 TypeOK 违例，说明模型在到达目标错误之前已出现其他问题，该结果不被视为重现了目标错误。工具同时校验 TLA+ 工具链的版本与校验和，将 TLC 的临时状态隔离在代码库之外，并报告状态数、搜索深度与耗时。

工作流分为五种模式：design 用于在实现前建立需求模型；diagnose 用于把已观察到的故障构造为可复现的反例，不修改产品代码；refine 用于对齐模型与实现并补充受控测试；review 与 verify 为只读模式，分别用于审查语义缺口和重新执行已有检查、发现漂移。
