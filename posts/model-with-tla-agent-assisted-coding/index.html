给 Coding Agent 加一道模型检查：用 TLA+ 找出并关上并发与生命周期问题

以一个旧回调写入新资源的 bug 和一次真实项目经历为例，介绍 model-with-tla：让 Coding Agent 用 TLA+ 把并发与生命周期的概念写精确，用 TLC 在修复后给出有范围的穷举结论，并用负向见证确认这个结论不是空洞的。

TLA+Coding AgentModel CheckingFormal Methods并发系统

一个后台任务正在处理资源 worker-A。任务还没完成，worker-A 被删除并重建，新资源沿用了同一个名字。随后旧任务的回调到达，提交逻辑只比较名字，于是把旧结果写进了新资源。

为了区分这两个 worker-A，下文把同一个逻辑名下的每一代实体称为一个 incarnation：删除前是第 1 代，重建后是第 2 代。旧回调带回的是为第 1 代计算的结果，却提交到了第 2 代上。

这个 bug 里每个函数单独看都没错，正常路径的测试也能通过。出错的是事件顺序：结果产生时有权写入，等到提交时，这个权限已经随着资源替换失效了。只要测试没有专门构造“启动、替换、回调、提交”这条顺序，它就不会暴露，而写测试的人或 Agent 得先想到这条顺序才会去构造它。

过去几个月，我在尝试把 TLA+ 放进 Agent-assisted coding，并把做法整理成了一个 Agent Skill：model-with-tla。做法是让 Agent 在写实现之外，再写一份描述系统状态和动作的模型。这份模型带来两样测试给不了的东西。一是写模型本身会逼出精确的定义：什么叫“已派发”，谁有权提交，谁负责清理。定义写下来再拿去对照代码，很多问题在这一步就暴露了。二是 TLC 会穷举模型里所有的事件交错：修复之前，它给出具体的反例；修复之后，它给出一个有范围的结论，即在给定的有限配置里，没有任何一种顺序会违反要求。它不证明代码正确，但能回答测试很难回答的问题：在这个范围里，还有没有我们没想到的顺序。

下面先用 worker-A 这个例子把建模、找反例、修复和回归检查完整走一遍，再讲一次真实项目里的经历，最后介绍 Skill 本身和使用方法。

测试循环漏掉了什么

失败反馈能帮助 Agent 修正已被测试表达的问题，却不能保证未被测试覆盖的事件交错会自行暴露。

Agent 的常规循环是写实现、跑测试、根据失败修代码。它很擅长修复已经被测试表达出来的问题，但能否发现 worker-A 这类 bug，取决于测试里是否已经有那条事件顺序。并发和生命周期问题难就难在这里：错误不是由某个输入值触发的，而是由几个动作的相对顺序触发的，可能的顺序又随动作数量快速增长。

TLA+ 换了一个出发点。你不写某条具体的执行路径，而是写清楚系统有哪些状态、哪些动作可以改变状态、哪些状态绝不允许出现。TLC Model Checker 随后在给定的有限配置里枚举所有可达状态，寻找违反要求的路径。

示意图：普通测试执行选定的场景；TLC 系统探索给定有限模型的可达状态。图中不代表实际覆盖率统计。

把例子写成 TLA+

模型不需要模拟程序的每一行，只需保留会影响“这次提交是否合法”的东西：资源当前是第几代、每个操作启动时绑定的是哪一代、操作进行到了哪一步，以及资源上最后一次写入来自哪一代的操作。

---------------------------- MODULE StaleCallback ----------------------------
EXTENDS Naturals

CONSTANTS Ops,             \* 可能并发的异步操作
          MaxIncarnation,  \* worker-A 最多被重建到第几代
          CheckIncarnation \* Commit 是否校验 incarnation

VARIABLES incarnation,  \* worker-A 当前是第几代实体
          opPhase,      \* 每个操作所处阶段
          opBinding,    \* 每个操作启动时绑定的 incarnation
          lastWriter    \* 当前资源上最后一次写入来自哪一代的操作，0 表示尚无写入

vars == <<incarnation, opPhase, opBinding, lastWriter>>

TypeOK ==
  /\ incarnation \in 1..MaxIncarnation
  /\ opPhase \in [Ops -> {"idle", "running", "done", "committed", "discarded"}]
  /\ opBinding \in [Ops -> 0..MaxIncarnation]
  /\ lastWriter \in 0..MaxIncarnation

Init ==
  /\ incarnation = 1
  /\ opPhase = [o \in Ops |-> "idle"]
  /\ opBinding = [o \in Ops |-> 0]
  /\ lastWriter = 0

StartOp(o) ==            \* 操作启动，记下此刻的 incarnation
  /\ opPhase[o] = "idle"
  /\ opPhase' = [opPhase EXCEPT ![o] = "running"]
  /\ opBinding' = [opBinding EXCEPT ![o] = incarnation]
  /\ UNCHANGED <<incarnation, lastWriter>>

Replace ==               \* 删除并重建 worker-A：名字不变，换一代实体
  /\ incarnation < MaxIncarnation
  /\ incarnation' = incarnation + 1
  /\ lastWriter' = 0
  /\ UNCHANGED <<opPhase, opBinding>>

Complete(o) ==           \* 异步结果返回
  /\ opPhase[o] = "running"
  /\ opPhase' = [opPhase EXCEPT ![o] = "done"]
  /\ UNCHANGED <<incarnation, opBinding, lastWriter>>

Commit(o) ==             \* 把结果写入当前叫 worker-A 的资源
  /\ opPhase[o] = "done"
  /\ CheckIncarnation => opBinding[o] = incarnation
  /\ opPhase' = [opPhase EXCEPT ![o] = "committed"]
  /\ lastWriter' = opBinding[o]
  /\ UNCHANGED <<incarnation, opBinding>>

Discard(o) ==            \* 丢弃已经过期的结果
  /\ opPhase[o] = "done"
  /\ opBinding[o] # incarnation
  /\ opPhase' = [opPhase EXCEPT ![o] = "discarded"]
  /\ UNCHANGED <<incarnation, opBinding, lastWriter>>

Next ==
  \/ Replace
  \/ \E o \in Ops : StartOp(o) \/ Complete(o) \/ Commit(o) \/ Discard(o)

Spec == Init /\ [][Next]_vars

\* 资源上的最后一次写入，只能来自绑定当前 incarnation 的操作
NoStaleWrite == lastWriter \in {0, incarnation}
=============================================================================

几处建模选择需要交代一下。

名字 worker-A 在模型里根本没有出现。它从不变化，所以“只比较名字”的提交逻辑在模型里等价于什么都不比较，也就是 CheckIncarnation = FALSE。Replace 把 lastWriter 置回 0，表示新一代资源上还没有任何写入。Ops 里放了两个操作，让 TLC 也去探索两个操作互相交错的情况，虽然最短的反例只需要其中一个。

要检查的性质 NoStaleWrite 是一个状态不变量：任何时刻，资源上的最后一次写入要么不存在，要么来自绑定当前 incarnation 的操作。直觉上更想写的是“每次 Commit 都必须获得授权”，但这是关于动作的性质，在 TLA+ 里要写成 [][\A o \in Ops : Commit(o) => opBinding[o] = incarnation]_vars 这样的形式，不能直接把动作放进 □。在这个模型里两种写法表达的是同一个要求；状态不变量读起来更直接，也能直接交给 tla-check 的 --expect invariant:NoStaleWrite。

配置文件 Buggy.cfg 对应有 bug 的实现：

CONSTANTS
  Ops = {o1, o2}
  MaxIncarnation = 2
  CheckIncarnation = FALSE
SPECIFICATION Spec
INVARIANTS TypeOK NoStaleWrite
CHECK_DEADLOCK FALSE

关闭死锁检查是有意的。所有操作结束、incarnation 也到达上限之后，模型没有后继状态，这是有限配置的自然终点，不代表系统卡死。

TLC 找到的反例

用 Skill 自带的 tla-check 运行这个配置，并声明预期结果是 NoStaleWrite 被违反：

"<skill-directory>/.tools/tla-check" check \
  --module "$PWD/StaleCallback.tla" \
  --config "$PWD/Buggy.cfg" \
  --expect invariant:NoStaleWrite

TLC 在探索了 28 个不同状态后报告违反，并给出一条 5 步的轨迹。下面摘自实际输出，省略了源码位置和整条轨迹中始终处于 idle 的 o2：

Error: Invariant NoStaleWrite is violated.
State 1: <Initial predicate>
/\ incarnation = 1  /\ lastWriter = 0  /\ opBinding = (o1 :> 0)  /\ opPhase = (o1 :> "idle")
State 2: <StartOp(o1)>
/\ incarnation = 1  /\ lastWriter = 0  /\ opBinding = (o1 :> 1)  /\ opPhase = (o1 :> "running")
State 3: <Replace>
/\ incarnation = 2  /\ lastWriter = 0  /\ opBinding = (o1 :> 1)  /\ opPhase = (o1 :> "running")
State 4: <Complete(o1)>
/\ incarnation = 2  /\ lastWriter = 0  /\ opBinding = (o1 :> 1)  /\ opPhase = (o1 :> "done")
State 5: <Commit(o1)>
/\ incarnation = 2  /\ lastWriter = 1  /\ opBinding = (o1 :> 1)  /\ opPhase = (o1 :> "committed")

读这条轨迹不需要懂 TLA+：o1 在第 1 代时启动，资源被替换为第 2 代，o1 的结果返回，提交之后 lastWriter = 1 而 incarnation = 2。它和开头时序图里的四个事件一一对应（o1 就是图中的 Operation X），区别在于这条路径是 TLC 自己找出来的，不是我事先画好的。

修复与两份配置

修复就是 Commit 里那一行守卫：结果只有在绑定的 incarnation 等于当前 incarnation 时才能提交；过期的结果走 Discard，不再写入。为了让修复前后用同一个模型检查，我用常量 CheckIncarnation 控制这行守卫是否生效。下表是我在本机运行的三个配置，每次都在 1 秒内完成：

配置 MaxIncarnation CheckIncarnation 期望 TLC 结果 不同状态数
Buggy.cfg 2 FALSE invariant:NoStaleWrite 违反，5 步反例 28
Fixed.cfg 3 TRUE success 通过 224
Vacuous.cfg 1 FALSE success 通过 16

模型和三个配置都可以直接下载运行：StaleCallback.tla、Buggy.cfg、Fixed.cfg、Vacuous.cfg。

Fixed.cfg 是修复后的回归检查：

"<skill-directory>/.tools/tla-check" check \
  --module "$PWD/StaleCallback.tla" \
  --config "$PWD/Fixed.cfg" \
  --expect success

Buggy.cfg 在修复之后也不能删。它不再描述“当前代码”，而是一份负向见证：证明这个模型确实能表达并捕获目标错误。之后每次修改模型，两份配置都要重跑，一份必须通过，一份必须以 NoStaleWrite 失败。表里的第三行说明了为什么需要后者。

一个 PASS 什么时候才有意义

Vacuous.cfg 用的是有 bug 的提交逻辑，却通过了检查。原因很简单：MaxIncarnation = 1 时 Replace 永远不会发生，过期结果根本不存在，NoStaleWrite 自然不会被违反。这个 PASS 什么都没有证明。

model-with-tla 把这一点叫作模型的 discriminability：模型不仅要允许正确行为，还必须能表达并到达目标错误。对重要的 Safety 性质，要准备一份像 Buggy.cfg 这样的负向见证（negative witness），确认 TLC 会因为预期的那条性质失败。

由 Agent 写模型时，还要防一种情况：模型被改到恰好通过。要得到 PASS，并不一定要修复任何东西。我在同一个模型上演示了两种改法，都没有改动有 bug 的提交逻辑：

  • 削弱性质：把 NoStaleWrite 改成 lastWriter <= incarnation。旧结果写入新资源时，1 <= 2 依然成立，检查通过；
  • 给环境动作加过强的守卫：要求 Replace 只能在没有进行中操作时发生。TLC 同样通过，只探索了 41 个状态。但产品无法阻止用户在操作进行中删除资源，这个守卫等于把 bug 假设掉了。

再加上前面的“缩小常量”，三种改法都会让模型恰好通过。它们也都会让 Buggy.cfg 不再失败：我用 --expect invariant:NoStaleWrite 重跑负向配置，tla-check 报告实际结果是 success，与预期不符，以退出码 4 结束。这三种改法是我为演示构造的；在我翻过的会话记录里，没有看到 Agent 为了通过检查而这样改模型。但只要任务被表述成“让检查通过”，它们就都是现成的捷径，负向见证能把这些捷径堵上。

记录里真实出现过的，是无意中写出的空洞模型。在一个工作项目里，Agent 给一个委托授权网关建模时写下了这样一行：

/\ startedWithAuthority' = startedWithAuthority /\ active /\ approved = payload

本意是把三个条件的合取赋给 startedWithAuthority'。但在 TLA+ 里 = 的优先级高于 /\，这一行实际被解析成 (startedWithAuthority' = startedWithAuthority) /\ active /\ (approved = payload)：变量保持原值，后两项变成了这个动作的守卫。startedWithAuthority 因此永远不会变成假，要检查的授权性质也永远不会被违反。正向配置照常通过；暴露问题的是负向配置，它们预期违反 AuthorizedEffect，实际却通过了，tla-check 报告结果不匹配。加上括号之后，负向配置按预期失败。同一个会话里，大约 80 分钟后，Agent 在另一个模型里犯了同样的错误，也是被负向配置拦了下来。

它也有边界。负向见证只能确认你想到的那类错误可以被捕获，不能发现你根本没有建模的状态或动作。模型遗漏了什么，仍然要靠需求核对和人的审查。

一次真实的使用：kinmesh 的认领协议

worker-A 是为这篇文章写的小例子，每个配置一秒内跑完。真实项目要复杂得多。下面是我在个人项目 kinmesh 里用 Claude Code 走这套流程的一次经历，发生在 2026 年 11 月 14 日，前后大约十个小时。文中的数字都来自那次会话的记录和仓库提交。

kinmesh 让 agent 处理团队里的消息。消息进入 Inbox 后，worker 认领一条投递（delivery），把它派发到执行 agent 的后端 T3，再观察 T3 上的 run 是否结束。当时计划引入运行槽位（run slot）：每个 agent 同时运行的 run 有上限，卡住的 run 要让出槽位，同一个任务同时只能有一个 run。动手实现之前，我让 Agent 先用 model-with-tla 给这套认领协议建模。

这个模型（Inbox.tla，416 行）覆盖了两个 worker 之间的租约竞争、worker 卡住或崩溃后带着过期状态回来、T3 上的 run 可能永远不结束，以及人可以停止等待、取消或恢复一条投递。它声明了 6 条安全性质和 2 条活性性质，并准备了 7 个已知错误的变体，每个对应一条性质。检查规模是 2 个 agent、2 个 worker、4 条投递。

前两个反例：一个错在模型，一个错在设计

第一次完整检查运行了一分钟左右，就给出了活性性质 QueuedDispatches 的反例。Agent 读完轨迹，判断问题出在模型本身：模型允许一个正常运行的 worker 在下一步之前就丢掉租约，而产品里的时限设定排除了这种情况。改成只有卡住的 worker 才会丢租约之后，第二次检查报告不变量 Settled 被违反：一条投递被人取消时，持有它派发租约的 worker 没有任何规则要求它放手，于是一直占着。这是协议设计里真实存在的缺口，它变成了后续实现必须满足的一条要求。

所以拿到反例之后还要先分诊。它可能说明设计有问题，也可能只说明模型对环境的描述不对，后者修的是模型，不是代码。

一条性质在 1700 万个状态里都没被检验到

7 个错误变体中，GiveWayFreesTask（让出槽位时连任务锁一起放掉）应当违反“同一任务同时最多一个 run”。它跑到 1700 万个状态都没有失败。原因在配置：积压上限 BacklogCap 设成了 1，第一个 run 让出槽位后积压就到了上限，派发随之暂停，同一任务的第二个 run 根本发不出去，任务规则也就从未起作用。换句话说，正向检查对这条性质的通过是空的。这和上文 Vacuous.cfg 是同一类问题，只是藏在一个 400 多行的模型里，没有负向变体就不会被发现。

把上限改成 2 之后，这个变体 3 秒就失败了。新增的上限为 2 的安全性配置检查了 3.14 亿个状态，全部通过。

状态空间爆炸

带活性性质的完整检查用单线程跑了 8 个小时还没结束，活性检查的状态图占了 5.6 GB，磁盘只剩 26 GB 可用。状态主要来自 2 个 agent 与 2 个 worker 的交错组合，而不是哪个单独的动作。

Agent 随后精简了模型：去掉不影响任何性质的 T3“等待审批”状态，把“在 T3 里停止”并入“结束”，用“卡住”来表示崩溃，并限制每次检查里人工操作的次数。精简后，4 条投递的安全性检查用 8 个线程、33 分钟、8500 万个状态通过。但加上活性之后，每分钟只能推进约 6 万个状态，估计要跑一天以上。它于是提议把检查拆开：4 条投递只查安全性，并按 worker 做对称化；活性改用 3 条投递的较小实例。

查到这里，我决定不再跑了。Agent 停掉了所有 TLC 进程，删掉运行留下的状态文件，共释放约 9 GB，并把 TLC 检查从 issue 的验收条件改成“建议，不强制”。模型仍然提交进了仓库，PR 里写明了验证到哪一步：4 条投递的安全性已通过；7 个错误变体都在各自的性质上失败，但那是在精简前的模型上确认的；精简后模型的活性没有验证。

修掉的 bug 来自模型与代码的对照

回头核对代码时，Agent 发现代码里没有明确的“已派发”标记，而是靠别的字段间接推断；模型里“已派发”的定义则是“启动记录已写入”。用模型的定义一对照，就暴露出一个当时就会触发的 bug：投递在真正发给 T3 之前就写好了启动参数，过期逻辑把“有启动参数”当成“可能已在 T3 里”，于是一条被退回队列、从没发出去的投递永远不会过期。

修复（7d032f2）让 worker 在调用 T3 之前，先在自己的租约下把投递标成 uncertain；如果租约已经丢了，就停在这一步，不去调用 T3。这个 bug 不是 TLC 反例直接给出的。写模型时，Agent 不得不给“已派发”下一个精确定义，拿这个定义对照代码，它才浮现出来。

几个小时后，模型被删掉了

当天下午，run slot 这套设计被“每个话题一段 agent 对话”的新方案取代，模型也随之删除（fb7ad95）。

回头看，这次的收获和代价都很具体。Settled 的设计缺口在开始检查后十几分钟内出现；空洞的变体是在检查进度时发现的；过期 bug 来自模型和代码的对照。之后数小时的活性检查没有给出新的反例，却占满了时间和磁盘。Agent 写一个 400 行的模型很快，但它倾向于写“完整”的模型；规模要控制在什么范围、哪些检查必须通过、哪些只作参考，最好在开始之前就定下来。

model-with-tla 做了什么

上面两个例子里，从写模型、配置到解读反例和设计负向见证，都由 Agent 起草。model-with-tla 要做的，是让这件事在日常开发里有章可循：Skill 告诉 Agent 什么时候值得建模、如何划定模型边界和定义性质、不同任务允许改哪些文件；TLC 负责穷举；tla-check 用固定版本的工具链执行 SANY 和 TLC，比对预期结果并输出结构化证据，让检查可以重复执行、结果可以机器判断。

从要求出发，而不是翻译现有实现

当前代码可能正是错误的来源。如果直接把实现翻译成 TLA+，TLC 全部通过也只能说明模型没有违反它自己声明的性质，不能说明实现符合产品要求。在 worker-A 的例子里，如果 Agent 照着代码只建模名字，NoStaleWrite 这条性质根本写不出来。

所以 Skill 要求把几类信息分开记录：产品要求和已确认的设计决策、当前实现的行为、外部系统提供的保证，以及尚未证实的假设。例如，外部 API 调用超时并不能证明操作没有执行。如果业务要求避免重复副作用，模型就必须保留“操作已成功但响应丢失”的可能，除非外部 API 有明确的契约排除它。

按要检查的性质决定切分点

模型的粒度由要检查的性质决定，而不是由源代码有多少函数决定。上面的模型把一次操作拆成 StartOp、Complete 和 Commit，因为 bug 只在“绑定 incarnation”和“提交”之间插入 Replace 时才会出现。如果把整个操作写成一个原子动作，Replace 就插不进去，TLC 也就找不到这个反例。Complete 和 Commit 分开，则是为了表达“结果已经返回、但还没决定提交还是丢弃”这个中间状态。

同样的考虑也适用于带外部副作用的调用：

图中分开了外部接受请求、响应是否送达与本地提交三个边界。右侧的超时分支意味着结果未知，而不是外部操作未发生。查看可缩放的 SVG 原图。

外部操作已经生效、本地却还不知道结果时重试，就可能产生重复副作用；同时到来的取消可以收回提交权限，却撤销不了已经发生的外部效果。反过来，日志写入或 UI loading 状态如果不影响待检查的行为，就不需要变成模型里的变量。

把反例变成测试

TLC 的反例是抽象的状态轨迹。Agent 需要把它映射到领域事件和代码里的关键边界，再写成可以重复执行的受控测试。

这是一条语义映射链，不是模型结果自动证明实现正确的推导链。

上面那条 5 步轨迹对应的测试是：启动操作后，在回调处暂停它（State 2）；删除并重建 worker-A（State 3）；放行回调（State 4、5）；最后断言第 2 代资源的状态没有被旧结果修改，这对应 NoStaleWrite。测试要保留反例中的身份、事件顺序和被检查的性质，正常路径的成功测试替代不了它。

核对模型、实现和外部证据

模型通过不等于代码通过。模型可能把某段行为当作原子操作，而实际代码在两条语句之间允许别的任务插入；模型区分了 incarnation，实现却可能仍然只用可复用的名字。所以 model-with-tla 会分别收集不同来源的证据，并核对它们是否使用一致的身份、操作和终态语义。

这些是需要相互对应的证据来源，不是一个 PASS 就能逐层自动推出后续结果的流程。

证据不完整时，工作流不会笼统地报告“已验证”，而是给结论标上一个状态：

  • closed：结论需要的每一层证据都在，且语义对得上；
  • scoped：内部行为有证据支持，但平台、兼容性或时序方面的结论只在记录过的环境里成立；
  • drifted：证据曾经对齐，但模型、实现、工具链或外部环境后来变了；
  • blocked：某个前提缺失，证据无法收集，这既不说明通过，也不说明失败；
  • unproved：关键的一层缺失、互相矛盾、空洞（比如上面的 Vacuous.cfg），或者依赖没有依据的假设。

在 Coding Agent 中使用

安装与调用

Skill 随 ronhuafeng-engineering 插件发布。在 Claude Code 里：

/plugin marketplace add ronhuafeng/skills-release
/plugin install ronhuafeng-engineering@ronhuafeng-skills

在 Codex CLI 里：

codex plugin marketplace add ronhuafeng/skills-release --ref main
codex plugin add ronhuafeng-engineering@ronhuafeng-skills

本机还需要 Java 11 或更新版本和 uv。TLA+ 工具链和 tla-check 已经打包在 Skill 里，不用另外下载。

这个 Skill 设置了 disable-model-invocation，Agent 不会自己决定调用它，需要你显式调用并指定模式。在 Claude Code 里，kinmesh 那次的调用方式是：

/ronhuafeng-engineering:model-with-tla design 给 Inbox 的认领协议建模。安全性检查用 2 个 worker、3 条投递，单次不超过 10 分钟；每条安全性质配一个负向配置；活性检查只作参考，不作为验收条件。

后半句是 kinmesh 留下的教训：检查规模和时间预算、哪些检查必须通过，最好在开始时就写进请求里，而不是等 TLC 跑了几个小时再决定。

五种模式

Skill 把工作分成五种模式：

模式 什么时候使用 主要结果
design 开始设计具有复杂生命周期或并发行为的新功能 建立需求模型，检查 Safety 和 Liveness
diagnose 已经观察到故障，希望定位其时序原因 构造并解释可复现反例，不修改产品代码
refine 已有需求模型，需要修改实现或低层模型 对齐模型与实现，补充受控测试
review 需要审查模型和实现之间是否存在语义缺口 只读检查，报告可操作的问题
verify 需要重新执行已有检查或发现漂移 只读验证，报告检查结果与证据边界

开发一个包含异步任务、取消和重试的功能之前，可以先用 design 模式让 Agent 整理状态和操作边界、构造模型并检查性质。已经出现故障时，先用 diagnose 保留现有实现、复现错误路径，比如得到上面那条 5 步轨迹；确认问题后再用 refine 修改代码和测试。已有模型的项目可以用 verify 重跑 Buggy.cfg 和 Fixed.cfg 这样的检查，看代码与模型是否还遵守同样的身份、生命周期、外部副作用和终态语义。Skill 也会按任务只加载需要的参考文档，而不是每次都让 Agent 处理全部形式化概念。

tla-check 比较的是预期结果和实际观察到的结果，而不只是进程是否正常退出。支持的预期包括 success、invariant:<name>、temporal、deadlock 等。比如负向配置期望的是 NoStaleWrite 被违反，如果 TLC 先报告了 TypeOK 违反，说明模型在到达目标错误之前就出了别的问题，这不算重现目标错误，tla-check 会报告不匹配。它还会校验 TLA+ JAR 的版本和校验和，把 TLC 生成的临时状态隔离在仓库之外，并在结果里给出状态数、搜索深度和耗时。这些机制不判断抽象是否正确，但能减少 Agent 在工具调用、版本漂移和结果解释上的出错空间。

拒绝旧结果之后：副作用和清理

上面的修复只解决了一半问题。假设 o1 不仅返回结果，还在外部系统里创建了一块磁盘，那么 Discard 拒绝了提交，这块磁盘依然存在。接下来要回答的是：谁负责清理它，清理是否被确认完成，清理失败时系统应该停在什么状态，以及系统最终能否回到一个没有孤儿资源的稳定状态。

这些问题对应着 Skill 参考文档里的几个概念：effect ownership 记录外部资源由哪个操作负责；cancellation 处理取消能收回什么、收不回什么；convergence 要求系统在有限步内到达稳定终态。提交权限和清理责任可以分离：过期操作已经无权写入新资源，却仍然要为自己创建的外部资源负责。

这不是假想的问题。在一个工作项目里，一套控制面负责开启和关闭临时的远程开发环境，关闭时要取消代码托管平台上正在运行的 CI 任务。一次平台局部故障中，查询任务状态的请求返回了 520：关闭已经记下了，取消请求却没有发出去，任务一直在跑。Agent 最初的修复只是去掉了那次状态查询。随后用 model-with-tla 复查，原模型把 Close 当成一步；拆成“记录关闭意图”“发出取消”“平台确认取消”三步之后，问题才清楚：关闭一旦记下，再次执行 Close 就不再有权发出取消，取消的责任在中间状态里丢掉了。最终的修复把“待取消”作为一项持久状态保存下来，只在平台接受取消之后才清除，并用不变量 CancelResponsibilityRetained 检查它。模型没有发现这次事故，但它让修复的范围从“删掉一次查询”扩大到“保留取消责任”。

很多时序问题的根源并不只是执行顺序，而是系统在状态变化之后，仍然沿用了旧操作的权限、观察或责任假设。要检查这一半问题，上面的模型还需要增加外部资源和清理动作；这里不再展开。

结论的边界

前面讲的是一次 PASS 会不会是空洞的。即使不空洞，它覆盖的范围也有限。

第一，TLC 检查的只是指定的模型和配置。模型遗漏了某个状态，或者配置把错误路径排除在外，检查通过并不能证明被遗漏的行为是安全的。Vacuous.cfg 就是后一种情况。

第二，Safety 和 Liveness 依赖不同的条件。Safety 检查坏事是否可能发生；Liveness 检查在规定的假设下，好事是否最终会发生。比如，给 Complete 加上弱公平（weak fairness），模型里的响应就一定会最终到达；但这等于假设外部服务最终会响应。它是一条需要单独声明的环境假设，而不是 TLC 验证出来的结论。

第三，模型和实现之间的映射需要单独验证。有限模型检查、受控代码测试和真实平台观测是不同层次的证据，不能互相替代。Skill 里的 model adequacy（模型是否足以支撑结论）、refinement（低层模型或实现是否遵守高层模型）和 evidence closure（上面那组状态标注）就是为了在自动化过程中保住这些边界。它们让结论更容易审查，但不能消除模型建错、需求不完整或外部系统违反假设的风险。

什么时候值得用

这个组合的价值不在于让 LLM 完成形式化证明。LLM 仍然负责理解系统、设计抽象和解释结果，也仍然可能遗漏状态或误解需求。变化在于，一旦模型和性质写定，探索执行路径的工作就交给了 TLC，而不再依赖 LLM 逐条猜测事件顺序。由此带来两个实际的好处：

  • TLC 的反馈独立于 LLM 自己的判断。比起让 Agent 再读一遍自己写的代码，一条有明确状态和顺序的反例更容易变成可复现的工程问题；
  • 重要的时序假设被留成了可以重跑的模型和配置，而不是只存在于某次对话、某条代码审查意见或某个临时测试里。

回看过去几个月的会话记录，TLC 很少是第一个发现 bug 的。大多数违反来自有意构造的负向配置，或者问题先被测试、代码审查复现，再写进模型。发现问题的时刻，多数在写模型的过程中：为了写出模型，Agent 必须把“已派发”“取消责任”“授权”这些概念定义清楚，再拿定义去对照代码。kinmesh 的 Settled 缺口是少数由反例直接指出的例外。

但发现只是一半。测试复现了一条出错的顺序，修复后这条顺序通过，说明的是这一条顺序不再出错。TLC 对修复后的模型做穷举检查，说明的是在给定的有限配置里，没有任何一种事件交错会违反这条性质；负向配置再确认这条性质确实能被违反，通过不是空洞的。取消责任那个例子里，测试检查的是写出来的几条顺序，CancelResponsibilityRetained 则在模型的全部可达状态上成立；kinmesh 的安全性检查覆盖了 4 条投递下的 8500 万个状态。这是有边界的证明：它覆盖的是模型和配置，不是代码本身，也不是任意规模的系统。但它回答的恰恰是测试难以回答的问题：除了我们想到的那条顺序，还有没有别的。

所以在这套流程里，建模首先是一种强制精确化的设计审查，负责把问题找出来；TLC 的主要作用则是在修复之后，为“这一类问题已经关上”给出一个有明确范围的完备性结论。

成本的差别很大。worker-A 的模型 60 多行，每个配置 1 秒内跑完；kinmesh 的模型 416 行，带活性的完整检查 8 小时都没跑完。运行成本主要取决于有多少个参与者互相交错，而不是模型写了多少行。不管哪种规模，最需要人判断的都是决定模型保留什么、确认负向见证成立、给检查定预算。这些 Agent 可以起草，但也正是它最容易出错的地方。

因此，并不是所有代码都值得建模。纯展示性的 UI、静态内容或没有复杂生命周期的确定性操作，用普通测试和代码审查通常就够了。值得建模的是涉及并发请求、异步回调、资源替换、重试和去重、取消后的副作用、事务中间状态、超时恢复，或者有“必须最终完成”这类进展要求的系统。尤其是那些正常路径容易实现、异常路径却会改变资源身份、操作权限或副作用责任的功能。这类错误一旦进入线上，往往很难靠日志和偶发的集成测试复现。

结语

Coding Agent 让实现变快了，但实现变快并不会自动带来对并发行为和生命周期边界的理解。model-with-tla 尝试在日常开发中加入一条不同的反馈路径：从行为要求出发写出可检查的状态机，让 TLC 寻找反例，并在修复之后对整个有限配置给出穷举结论，用负向见证确认这个结论不是空洞的，再通过受控测试和外部证据核对实现。

它不打算为每段代码提供完整的形式化证明。它要做的，是把那些过去停留在开发者直觉里的时序假设，变成可以表达、检查、反驳和回归验证的工程对象，让 Coding Agent 不只负责写出一个实现，还能系统地去找这个实现可能违反的行为契约。
