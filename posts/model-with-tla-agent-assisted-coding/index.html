model-with-tla：TLA+ 为什么在 Agent-assisted coding 中有效？

分析 model-with-tla 如何把 TLA+ 建模、TLC 反例、refinement 与实现证据连接成 Agent-assisted coding 工作流，以及它对时序、并发和生命周期缺陷的价值与边界。

TLA+Coding AgentModel CheckingFormal Methods并发系统

Optimized question (English): How does model-with-tla work end to end, and why is TLA+-based formal modeling particularly effective at discovering temporal, concurrency, and lifecycle bugs in agent-assisted coding? What makes this workflow more reliable than conventional AI-generated code reviews and tests?

我阅读了你仓库中的 SKILL.md 和五个核心命令。我的核心判断是：

model-with-tla 的价值，不只是让 Coding Agent 使用 TLA+，而是把 Agent 的一部分工作从「生成看起来正确的实现」转变为「构造可检查的行为契约，主动寻找违反契约的执行路径，再用这些反例约束实现」。

这解决了 Agent-assisted coding 的一个重要弱点：

LLM 擅长生成合理的执行路径，但不擅长系统性地发现所有可能导致错误的执行顺序。

TLA+ 的 model checking 恰好提供了另一种能力：在明确的有限状态空间内，系统地探索不同的状态转换和操作交错，寻找违反指定性质的路径。

而你的 workflow 又解决了单独使用 TLA+ 的另一层问题：一个通过 TLC 检查的模型，如何真正约束生产代码，而不是成为一个与实现脱节的形式化文档。

一、model-with-tla 实际是怎样工作的？

你的设计可以概括成一条证据链：

最值得注意的是，你没有把上述流程做成一个只有单一路径的自动化脚本，而是拆成了五种不同的任务模式：

Command 职责 关键边界
design 定义行为契约，设计并检查 TLA+ 模型 不把现有实现当作正确性标准
diagnose 将已观察到的故障转化为可复现反例 不修改产品代码
refine 将模型约束映射到低层模型、适配器、测试或实现 不暗中弱化原契约
review 检查需求、模型、实现和证据之间是否一致 只读
verify 重新执行既有检查，发现模型与实现之间的漂移 只读，不修改检查标准

这五种模式实际上覆盖了软件开发中不同的验证时机：设计前、故障调查中、实现修改时、代码审查时，以及回归检查时。

从工程角度看，这种分工很重要。因为「发现问题」「定义正确行为」「修复代码」「证明修复有效」是不同的任务，混在同一个 Agent prompt 中，容易出现为了让结果通过而修改判定标准的问题。

来源：SKILL.md、commands。

二、真正关键的机制：不是跑 TLC，而是防止「错误的模型得到正确的结果」

读完 references/model-adequacy.md、concurrency-contracts.md 和 evidence-closure.md 后，我认为这里有四个特别关键的设计。

1. 先验证模型是否有能力发现目标错误

假设系统只能选择 primary 或 alternate 两个目标，而要求是永远不能错误地选择 alternate。

如果 Agent 写出：

Targets == {"primary"}
NoAlternateTarget == target # "alternate"

TLC 自然会通过，但这并没有提供有意义的保证，因为错误状态从一开始就不在状态空间中。

你的 workflow 不满足于 positive check，而是要求建立能够区分正确与错误的模型：

  • 触发错误的前置条件必须可达。
  • 被禁止的结果必须能够表示。
  • 错误动作或负向模型必须能够产生那个结果。
  • 检查必须因目标性质被违反而失败。
  • 修正后的模型必须阻止同一故障。

这就是你在 model-adequacy.md 中强调的 Safety discriminability。

它在 Agent-assisted coding 中尤其重要。LLM 很容易生成看起来符合需求的模型，同时无意中把真正危险的状态排除掉。没有 discriminability 检查时，形式化验证也可能成为一种更有说服力的虚假安全感。

2. 抽象粒度由正确性决定，而不是由代码结构决定

这是整个 Skill 中我认为最有工程深度的一点。

你的规则不是「一个函数对应一个 TLA+ action」，而是：

只有当一个中间点的延迟、失败或其他操作插入能够影响待检查的性质时，才需要将它拆成独立的 action。

例如一个 API 调用在代码中看起来只有一步：

createResource()

实际可能包含：

commit intent
    ↓
send external request
    ↓
external effect accepted
    ↓
response returned / lost
    ↓
commit resource identity

这里的 external effect accepted 和 response returned 之间必须允许交错，因为外部操作可能已经成功，但响应丢失。

如果 Agent 将整个 API 调用建模为一个原子 action，相关的重复执行、错误重试、资源泄漏等问题就无法出现。

反过来，loading indicator、普通日志或不影响目标性质的 metrics，通常不需要单独建模。

这就解决了两个相反的问题：过度抽象会遗漏 bug；过度细化会导致 state explosion。

你实际上定义了一套以正确性为导向的 abstraction policy，而不是简单的建模模板。

3. 区分现实、观察和操作权限

这是很多时序错误的真正根源。

例如：

  • resource absent 不等于 resource observation failed
  • request cancelled 不等于 external effect cancelled
  • callback delivered 不等于 fresh state observed
  • same resource ID 不等于 same resource incarnation
  • operation timed out 不等于 cleanup completed

这些区分在普通代码中经常被压缩成一个 status、一个 Boolean 或一个对象 ID。

你的 identity-and-epochs.md 显式区分 stable identity、resource incarnation、observation revision、operation identity、attempt budget、policy scope 和 effect ownership。

这样一来，Agent 需要回答的不再只是「操作成功了吗」，而是：

「这个结果属于哪次操作、哪个资源生命周期？它现在是否仍有提交权限？即使不能提交结果，它是否仍负有清理已产生外部副作用的责任？」

这比单纯检查 data race 更深入。它检查的是随时间变化的 authority、knowledge 和 responsibility 是否被正确维护。

4. 让反例真正进入实现验证，而不是停留在模型里

TLC 发现反例后，你要求将其转换成领域事件链：

initial state
→ actor / action
→ authority or effect change
→ forbidden result
→ violated property
→ implementation seam
→ controlled test order
→ remaining external assumption

这一步将形式化结果转化为 Agent 可执行的工程任务。

同时，refine 要求明确区分 focused obligation、finite-checked refinement 和 proved refinement，不允许因为某个局部 invariant 通过，就宣称整个实现满足高层规范。

evidence-closure.md 进一步要求把模型、受控测试、真实外部环境和最终收敛状态分别记录为证据，并用 closed / scoped / drifted / blocked / unproved 分类。

换句话说：你要求 Agent 证明它的结论处于哪一个证据边界，而不只是展示一个成功的检查结果。

这与 TLA+ 本身的能力边界一致：TLC 可以系统检查给定有限模型的状态空间，但结果不会自动推广到任意规模或真实实现。

还有一个容易忽略的细节：你实现了独立的 tla-check 执行器，固定工具版本及校验和，先检查 SANY，再执行 TLC，并比较预期结果和实际结果的精确类型。

例如预期是 invariant:NoDuplicate，但实际首先违反的是 TypeOK，就不能报告「已经成功重现重复执行问题」。

这使得自动化验证不再只是检查命令是否返回非零，而是检查是否真的获得了想要的证据。

来源：model adequacy、evidence closure、TLC tool。

三、为什么这种方法在 Agent-assisted coding 中特别有效？

我认为它的有效性来自三个层面的互补。

1. LLM 负责构造模型，Model Checker 负责对抗模型

普通 Coding Agent 的主要工作机制是基于上下文生成代码、解释和测试，再依据执行反馈进行修正。

它可以推理并发问题，但在没有外部验证工具的情况下，很难系统覆盖所有可能的事件交错。

TLC 的搜索方式不同。

示意图：左侧是选定场景的执行，右侧是模型状态空间的系统探索；并非实际覆盖率统计。

因此，Agent 不需要自己准确猜中所有危险时序。它需要建立足够准确、足够有辨别力的状态机，然后让 TLC 搜索违反约束的行为。

两者分工可以概括为：

LLM 是 specification constructor 和 counterexample interpreter；TLC 是 deterministic state-space explorer。

这个分工比让同一个 Agent 同时编写实现、编写测试并主观判断是否正确，更容易暴露设计中的自相矛盾之处。

2. Agent 降低了形式化方法的边际成本

TLA+ 长期以来的主要阻力之一，不是其理论价值，而是建立合适抽象模型所需的专业知识与工程时间。

Agent 可以承担大量重复性工作：梳理状态变量、建立 action、编写 TLC 配置、读取错误轨迹、调整抽象、形成测试方案。

但更重要的是，你的 Skill 不让 Agent 任意增加状态和细节，而是通过 model-adequacy.md 规定哪些区别必须保留、哪些可以忽略。

这使 TLA+ 从一个可能需要专家专门开展的设计活动，转变为可以嵌入日常 Agent coding loop 的验证步骤。

也就是说，真正的变化不是 TLA+ 变得更强，而是使用形式化检查的成本结构发生了变化。

当生成和迭代模型的成本降低时，以往不值得单独投入形式化建模的中等复杂度异步 workflow，也开始具备较好的投入产出比。

3. 反例提供了高密度、可操作的反馈信号

一个普通单元测试失败，经常只能告诉 Agent 某个断言没有满足。

而一个有效的 TLC counterexample 可以告诉它：

哪个操作开始，哪个资源被替换，什么时候观察变得过期，哪个回调在什么条件下执行，以及哪个 invariant 首次被破坏。

这种反馈具有两个重要特征：它是有序的，而且是反事实的——展示了一个实现者可能没有考虑过、但模型允许发生的执行序列。

Agent 可以据此构造有针对性的 controlled test，而不是在多个函数里盲目修改代码。

反例因此成为形式模型和具体实现之间的一种中间表示。

四、用一个具体例子说明

假设有一个异步资源管理器，同一个逻辑资源 ID 可以在重启后被重新使用。

这里的 Authorized 是由产品契约定义的权限谓词，通常需要比较 incarnation、operation identity 和当前 policy 等。

普通测试很容易只覆盖资源没有被替换时的成功路径。

TLA+ 则可以显式表示两种 incarnation、资源替换 action、异步完成 action 和结果提交 action。只要模型保留上述错误行为，TLC 就有机会找到这条交错路径。

随后 Agent 将反例转成一个固定事件顺序的测试，验证旧回调不能修改新资源。

如果旧操作已经创建了外部副作用，还需要单独检查 effect ownership 和 cleanup responsibility，不能因为拒绝了 stale commit 就认为副作用也自动消失了。

这个例子也说明，很多所谓的时序 bug，本质上不是执行顺序本身有错，而是状态改变之后，旧操作仍被错误地授予了权限。

你的 identity-and-epochs.md 和 effects-and-convergence.md 正是系统性地处理这类问题。

五、哪些边界决定了这个 workflow 的实际可靠性？

我认为有三个地方不能忽略。

第一，模型和性质本身可能是错的。 TLC 不能判断产品需求是否合理，也不能自动识别 Agent 是否遗漏了重要环境行为。你使用 governing requirements、model adequacy 和 negative witness 来抑制这一问题，是正确方向，但不能完全消除同一个 Agent 同时理解需求和编写模型所带来的共同错误风险。

第二，Safety 比真实环境中的 Liveness 更容易得到明确的有限验证。 例如，对 callback completion 施加 weak fairness，并不能保证外部系统真的发送 callback。WF 解决的是持续 enabled 后的调度问题，不是外部事件的到达保证。你的 model-adequacy.md 明确区分 environment enablement 与 local scheduling，我认为这是避免虚假进展保证的重要防线。

第三，模型通过不等于实现通过。 即使一份 TLA+ 模型没有发现错误，如果代码没有保持相同的原子性、身份、epoch 和 effect 语义，也可能在真实运行时违背模型。你的 refinement mapping、controlled trace 和 evidence closure 能降低这种风险，但普通测试只能提供相应范围内的一致性证据，不能自动证明完整的代码 refinement。

从仓库实际配置看，Skill 采用 user-invocable: true 和 disable-model-invocation: true，也就是说它是一个显式选择的工作流，而不是所有编码任务自动强制执行的后台机制。这也合理：对于存在竞争、重试、取消、外部副作用或进展要求的系统，它更有价值；对于纯 UI 或简单确定性逻辑，建模成本可能不值得。

另外，仓库里的 evaluation cases 和 oracles 是人工评估规范，而不是已执行的量化实验。因此，你几个月来的有效性观察具有实践意义，但仅凭公开文件还不能得出缺陷发现率提升了多少的统计结论。

六、我认为它更深层的工程意义

我会把 model-with-tla 看作一种 Agent-mediated executable specification and evidence workflow。

它将三个原来相对分离的环节连接起来：自然语言需求、可执行的形式化行为规范、受控实现证据。

这条连接很关键，因为 Agent-assisted coding 容易扩大代码生成的规模和速度，而代码生成得越快、跨越的状态边界越多，单靠人类 code review 和 happy-path tests 就越难维持相同的正确性信心。

model-with-tla 并没有让 Agent 获得无限的推理能力，而是引入一个独立于 LLM 语言判断的、可以反复运行的状态空间检查机制，并且为检查结果规定了严格的适用边界。

因此，我认为它有效的根本原因是：

它把 Agent 从以「完成实现」为中心的工作方式，推动到以「构造可证伪的行为契约，并持续收集与之匹配的实现证据」为中心的工作方式。

其中，TLA+ 负责让时序假设显式化，TLC 负责尝试推翻它们，Agent 负责在抽象模型、反例和实际代码之间建立联系。

这三者的组合，才是这个 workflow 真正有价值的部分。
