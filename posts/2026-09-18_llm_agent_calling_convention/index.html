从对话到调用约定：为 LLM Agent 设计 Stack、并发与进程模型

从一次不污染主会话的临时推理出发，本文逐步把 LLM Agent 的 message list 理解为 activation frame，并进一步推导出 calling convention、immutable prefix、KV cache、structured concurrency 与 CSP-style process/channel 的统一运行时模型。

很多 Agent 设计都从“对话”开始思考：有一个 thread，里面保存 message history；用户继续说话，模型继续回答；工具调用和工具结果也继续追加进去。

这个模型很直观，也很容易工作。但当一个会话变长，或者 Agent 开始做更复杂的子任务时，我越来越觉得，“对话”可能只是表面形态，不是最合适的运行时抽象。

促使我重新思考这个问题的场景很简单：假设当前已经有一段很长的 session，我只想临时问模型一句“总结到目前为止发生了什么”，拿到结果以后继续原来的工作。我不希望这次总结请求和总结结果永久写进原 session，因为它们只是一次辅助计算，不是主会话历史的一部分。

最初的想法只是：从当前 thread fork 一个临时 child，在 child 里发消息，取回回答，然后丢掉 child。

但继续推下去以后，我发现真正有价值的并不是“临时 thread”这个 helper，而是一套更像编程语言的 LLM calling convention。

如果这个判断成立，那么 thread、message、tool、并发、后台任务和 KV cache 都会获得一个更统一的解释。

第一步：不要把临时计算写回主会话

设当前 thread 的上下文是：

[A B C D]

我现在要做一次辅助计算：

summary = summarize(current_context)

最直接的聊天式实现会变成：

[A B C D
 User: summarize everything above
 Assistant: ...]

问题在于，为了计算一个 summary，我永久修改了被总结的对象。

这在普通程序里很奇怪。函数调用通常不会为了求一个返回值，把函数内部的局部状态全部写回 caller 的局部状态。更自然的行为应该是：

Parent:
[A B C D]

Call:
[A B C D] + [summarize request] + [callee execution]

Return:
summary

Parent:
[A B C D]

因此，第一个重要区分出现了：

一次模型计算的内部轨迹，不一定应该成为调用者的长期 conversation history。

这也是为什么“Stacked Thread”作为最初的使用体验是有价值的，但不应该马上变成一个新的长期对象类型。真正需要抽象的不是一种特殊 thread，而是一个 call boundary。

第二步：message list 更像 activation frame，而不只是 history

为什么函数调用这个类比会越来越自然？因为 LLM Agent 的一次输入，本来就不是简单的一段文本。

一个现代 Agent context 往往包含多种不同类型的记录：

System instruction
Developer instruction
User message
Assistant message
Tool call
Tool result
Observation
Structured output
...

它更接近一个按顺序排列的 tagged record stream，而不是 []string。

传统 stack frame 也不是“一坨内存”。它是按照 calling convention 组织的一组异构状态，例如参数、返回地址、保存的寄存器、局部变量和临时值。它们类型和作用不同，但共同构成一次 function activation。

从这个角度看，LLM 的 message list 很像一种 serialized activation record：

LLM Invocation Frame
┌─────────────────────────┐
│ inherited instructions  │
│ inherited messages      │
│ call arguments          │
│ tool calls              │
│ tool results            │
│ local observations      │
│ return candidate        │
└─────────────────────────┘

这个类比的关键不是说 Transformer 内部真的有传统 CPU stack，而是说两者在运行时语义上非常接近：

caller frame              ≈ parent thread/context
call site                 ≈ fork point
arguments                 ≈ new input messages
inherited environment     ≈ prefix context
locals / temporaries      ≈ child-local messages and tool traces
return value              ≈ final result
exception                 ≈ failed/interrupted run
frame unwind              ≈ discard/unsubscribe child

于是 history 这个词开始显得太弱。它只强调“以前发生过什么”，而这里真正重要的是 execution context layout。

第三步：从 fork 走向 calling convention

单独的 fork 只是 branching：

       A
      / \
     B   C

它并不自动意味着函数调用。

函数调用还需要额外约定：callee 有自己的局部执行状态；callee 最终产生一个 return value 或 error；callee 完成以后，其局部 frame 被 unwind；caller 是否使用返回值，由 caller program 决定。

因此，更完整的 LLM call 可以写成：

caller context
      │
      │ CALL(arguments)
      ▼
construct scoped child frame
      │
execute one or more turns
      │
produce result / error
      │
unwind child frame
      │
      ▼
program receives result

这里我认为有一个非常重要的设计原则：

return value 默认进入 program memory，而不是自动写回 model context。

也就是说：

r, err := Call(ctx, req)

if useful(r) {
    // 程序决定是否、以什么形式，把结果带回主会话。
}

这会把 Agent runtime 中长期被混在一起的两类“内存”分开：

Model Context Memory
  messages
  instructions
  tool observations
  model-visible state

Program Memory
  variables
  validated results
  workflow state
  business state
  process handles

模型可以提出结果，但程序决定是否接受、保存、提交或重新注入上下文。这也延续了我在 llm-go 中采用的一条原则：

Models propose. Programs decide. Effects require authority.

这个原则在 call convention 中不再只是一句安全口号，而是一个明确的内存与控制边界。

第四步：不要发明第二套 Thread

当一个运行时已经有原生的 thread、fork、turn、interrupt 和 cleanup 机制时，一个诱人的设计是再加一个 StackedThread 对象，给它 Send、Close、Run 之类的方法。

我现在认为这不是最好的方向。

“Stacked”应该描述一种 调用关系和生命周期，而不是一种新的 thread 身份。

普通编程语言里也没有一种特殊的 StackedFunction。普通 function 进入 calling convention 后，才产生一个 activation frame。同样，普通 Agent thread 经过 scoped fork 和 call lifecycle 后，就可以承担 frame 的角色。

因此，更稳妥的分层是：

Protocol / mechanism
  fork
  start turn
  interrupt
  unsubscribe

Lifecycle composition
  Call
  Continue
  Fork + first turn

Usage patterns
  summarize
  critique
  verify
  speculative analysis
  what-if exploration

协议层保留协议事实，runtime 层提供生命周期组合，业务层定义用途。不要为了一个好听的比喻复制已有协议概念。软件系统已经有足够多“为了抽象而抽象”的纪念碑了。

第五步：真正的 stack 来自 active invocation chain

如果只有一个 parent fork 一个 child，那么“stack”这个词其实并不严谨，那只是 tree branching。

真正让 stack 语义成立的是递归调用：

A calls B
B calls C
C returns
B calls D
D returns
B returns
A continues

完整调用关系是一个 tree：

        A
        │
        B
       / \
      C   D

但任意同步执行时刻的 active path 是：

A
A → B
A → B → C
A → B
A → B → D
A → B
A

这就是 stack。

所以更准确的说法是：

数据结构可以是 context tree，而执行中的 active invocation path 是 stack。

这也意味着，Stacked Thread 最值得保留的含义不是 LIFO 容器，而是 stack-based conversational invocation。

第六步：immutable prefix 让语义和 KV cache 对齐

这个模型还有一个很实际的系统优势：它天然鼓励 immutable shared prefix。

假设 parent context 是：

[A B C D]

两个独立调用分别得到：

[A B C D X1 X2]
[A B C D Y1 Y2]

逻辑结构是：

          [A B C D]
           /     \
      [X1 X2]   [Y1 Y2]

如果底层 serving system 支持 prefix cache 或 KV reuse，那么这正是它喜欢的形态：公共 prefix 保持完全相同，每个 invocation 只增加自己的 suffix。

概念上可以写成：

logical context model       transformer cache model

caller prefix               shared KV prefix
callee-local suffix         branch-local KV suffix
fork point                  cache branch point
frame unwind                release branch-local cache

这里必须保持一个边界：这种调用约定 允许 KV/prefix cache 复用，但不应承诺某个具体 serving backend 一定复用。实际命中还取决于模型、token 序列、运行配置、cache residency、上下文压缩和服务端实现。

但从架构上看，这仍然很重要，因为它把正确的语义和高效的执行方向放在了一起：

Frame = Immutable Prefix + Local Suffix

而不是：

Frame = Mutate(Prefix)

当一个 100k token 的稳定上下文需要派生多个分析任务时：

100k-token prefix
   ├─ summarize
   ├─ critique
   ├─ extract actions
   ├─ verify
   └─ plan

这些任务在语义上本来就应该是独立 sub-computation；在支持 prefix reuse 的实现里，它们也可能共享大部分前缀计算。这个重合不是证明，但它是一个很强的架构信号。

第七步：conversation frame 隔离，不等于 effect 隔离

函数调用的类比还能解释另一个容易混淆的问题。

child frame 的 conversation timeline 可以是隔离的，但文件系统、数据库、网络、外部服务未必隔离。

这很像普通程序里的 stack 与 heap：

conversation-local state   ≈ stack-local state
filesystem / database      ≈ shared heap / external state
network / SaaS             ≈ external effects

函数返回以后局部变量会消失，但它对全局状态的修改不会自动消失。

同样，一个 ephemeral Agent frame 被 unwind，并不意味着它在 workspace 中修改的文件、发出的请求或创建的资源会回滚。

因此，调用约定必须和 effect authority 分开：

Frame isolation
    ≠
Effect isolation

如果未来需要更强的隔离，可以在另一层引入 read-only capability、workspace snapshot、transaction、sandbox 或外部 mutation approval。但这些是 effect system 的职责，不应该偷偷塞进“临时 thread”这个概念里。

这也是为什么程序应该拥有 policy 和 side effects：runtime 可以提供机制，应用决定权限、审批、沙箱和提交。

第八步：并发以后，不再只有一个 stack

单个同步调用很像普通 function call。但 Agent 最终一定会需要并发。

例如一个 parent 同时派生三个分析：

Parent
  ├─ Security analysis
  ├─ Performance analysis
  └─ API review

这时系统不能再被描述成“只有一个 stack”。更准确的模型是：

Invocation graph: context tree

Task 1 active stack:
Root → Parent → Security

Task 2 active stack:
Root → Parent → Performance

Task 3 active stack:
Root → Parent → API Review

也就是说：

context tree 描述所有 frame 的关系，每个并发 task 有自己的 active call stack。

这个结构自然导向 structured concurrency。

Structured concurrency：让 child lifetime 有归属

并发最麻烦的通常不是“能不能同时跑三个模型”，而是谁拥有它们的生命周期。

一个合理的 scoped fan-out 可以写成：

Parent Invocation Scope
      │
      ├─ Child A
      ├─ Child B
      └─ Child C
      │
      └─ join

这类 child task 应满足几个默认 invariant：

  1. child 从 call time 的 parent snapshot 开始，不会神奇地看到 parent 后续变化；
  2. parent scope 被取消时，child cancellation 向下传播；
  3. child completion order 不应自动变成 parent conversation order；
  4. child result 先进入 program memory，再由程序决定如何 join；
  5. failure policy 是显式 policy，例如 fail-fast、wait-all、best-effort 或 first-success。

第三点尤其重要。

如果三个并发 child 谁先返回，谁就先被自动 append 到 parent，那么：

same input
+ different network timing
= different conversation state

这会让系统把调度抖动误当成语义。更稳妥的方式是先收集 typed results，再由 deterministic caller logic 排序、筛选、验证和合并。

这仍然符合同一条原则：模型产生候选信息，程序决定接受顺序和提交方式。

第九步：Call、Task 和 Process 应该是三种不同东西

走到这里，还会遇到另一类问题：CI、部署、训练、后台服务、远程 job 可能运行几分钟甚至几小时。

如果把它们继续绑定在某个 LLM frame 上，就会得到非常别扭的生命周期：一个 conversation frame 为了等 CI 结束而挂十分钟，期间所有进展、日志和心跳还不断污染上下文。

这时，我认为应该明确区分三种执行原语：

1. Call
   scoped
   synchronous in semantics
   returns once
   stack-like lifetime

2. Task
   scoped concurrent child
   owned by structured concurrency scope
   joins back into parent program flow

3. Process
   long-lived
   may outlive creating frame
   runtime-owned
   communicates through channels/events

这三个概念如果全部混成一个 AgentRun，生命周期会很快变成一锅粥。

第十步：CSP-style process + channel 处理长生命周期活动

对于 CI 或后台进程，更自然的模型不是：

caller frame
   │
   └─ block for 10 minutes

而是：

caller
   │ spawn
   ▼
process
   │
   ├─ Started
   ├─ Progress
   ├─ LogChunk
   ├─ Failed
   └─ Completed

调用者拿到的不是最终结果，而是一个 process handle 或 capability：

type Process interface {
    ID() ProcessID
    Events() <-chan ProcessEvent
    Wait(context.Context) (ProcessResult, error)
    Cancel(context.Context) error
}

这里真正有启发的不是“channel 可以异步传消息”，而是 CSP 风格的一条基本思想：

长生命周期活动应该通过通信暴露状态，而不是要求某个 conversation frame 持续共享和轮询它的内部可变状态。

这也意味着 process event 应该是 typed event stream，而不是一串无差别文本：

ProcessEvent =
    Started
  | Progress
  | Output
  | Request
  | Completed
  | Failed

而 LLM context 应只接收真正值得进入模型决策的信息。

LLM context 不应该充当 runtime event log

这是整个模型里另一个重要结论。

考虑一个运行 20 分钟的 CI。如果 Agent 每隔十秒轮询一次，并把：

still running
still running
still running
...

全部写进 conversation，那么我们同时得到了三件坏事：context 膨胀、prefix 不稳定、模型注意力被低价值状态污染。

更合理的管线应该是：

Runtime Event Stream
        │
        │ filter / aggregate / select
        ▼
Relevant Observation
        │
        ▼
next LLM Invocation

后台 process 可以独立运行。只有当出现完成、失败、需要输入、重要阶段变化或超时等事件时，runtime 才构造新的 observation frame，让模型重新参与。

这与我此前在 《从工具调用到事件驱动：大语言模型智能体的运行时架构》 中讨论的 observer/planner 分工是同一个方向：高频 runtime signal 不应该直接变成高层模型上下文。

第十一步：CSP 并没有否定函数调用，而是补足它的作用域

我此前在 《谁在调用谁：用通信过程和协程理解大语言模型智能体》 中更强调 CSP、事件和协程，因为长任务确实无法被单一同步调用链很好地表达。

现在我更愿意把两种模型放在一起，而不是互相替代：

Short-lived scoped computation
    → Call / Stack

Concurrent scoped computation
    → Task / Structured Concurrency

Long-lived independent activity
    → Process / Channel / CSP

函数调用没有失效，只是过去我们让它承担了不该承担的所有生命周期。CSP 也不是“新的万能模型”，它更适合描述那些可以独立推进、产生事件、并且可能比当前 invocation 活得更久的活动。

这比把所有东西都叫 async 更有解释力。

第十二步：select 成为 Agent runtime 的自然控制原语

一旦 process 和 channel 存在，Agent runtime 很自然会遇到：

等待 CI 完成
等待用户输入
等待另一个 Agent result
等待 timeout
等待外部状态变化

这时 Go/CSP 风格的 select 是一个很有启发的控制模型：

select {
case r := <-ci.Done():
    // CI finished
case msg := <-userInput:
    // user changed the goal
case r := <-childResult:
    // another invocation returned
case <-timeout:
    // reconsider the plan
}

模型不需要成为唯一的事件发起者。用户、工具、observer、scheduler、外部服务和其他 Agent 都可以产生事件。runtime 负责选择、过滤和调度；模型只在需要解释和决策时被唤醒。

这使 Agent 更像一个运行在事件系统上的 planner，而不是一个永远占据主调用栈顶端的“主程序”。

第十三步：把这些模型放在一起

到这里，可以得到一个比较完整的 Agent runtime 图景：

                         Program
                            │
           ┌────────────────┴────────────────┐
           │                                 │
   Invocation Runtime                 Process Runtime
           │                                 │
      Call / Task                       Spawn / Channel
           │                                 │
   stack / fork-join                 long-lived activity
           │                                 │
           └────────────────┬────────────────┘
                            │
                      Event / Result
                            │
                            ▼
                     Program decides
                            │
                            ▼
                    next invocation

几个核心模型分别是：

Context model:
  persistent immutable-prefix tree

Synchronous execution:
  stack-based calling convention

Scoped concurrency:
  structured task tree

Long-lived execution:
  CSP-style processes + channels

Execution state:
  one active stack per task

Return model:
  results enter program memory first

Effect model:
  explicit authority over shared state

Caching model:
  shared prefix + branch-local suffix

这里有一个我认为很漂亮的结构对应：

persistent context tree
        ↕
structured concurrency tree
        ↕
KV prefix tree

而任意一个正在执行的 scoped task，只是这棵树上的一条 active path，也就是一个 call stack。

第十四步：这更像一个 execution ABI

继续抽象，可以把这套约定看成一种 LLM execution ABI：

1. Caller context
   当前可见的稳定 prefix

2. Call boundary
   fork point / snapshot point

3. Arguments
   本次新输入

4. Callee-local execution
   child-only turns, tools, observations

5. Return convention
   typed result / final response / error

6. Unwind
   scoped child lifetime ends

7. Effects
   external mutation follows separate authority rules

这套 ABI 的意义不是要求所有 provider 都实现完全相同的 thread API，而是提供一个更清晰的运行时思考方式。

底层 provider 可以使用 thread fork、prompt prefix、session snapshot、server-side cache 或其他机制。上层语义仍然可以保持一致：稳定 caller context + scoped local suffix + explicit return + explicit effects。

设计原则

如果把以上推导压缩成几条原则，我会保留下面这些：

第一，模型上下文是执行上下文，不只是聊天记录。 message list 可以被理解为 typed sequential activation record。

第二，调用应该有边界。 callee-local trajectory 默认不写回 caller；return value 先进入 program memory。

第三，context prefix 尽量不可变。 这既减少语义污染，也为 prefix/KV reuse 留出实现空间。

第四，frame isolation 与 effect isolation 分开。 临时 child 消失，不代表文件、数据库和网络副作用回滚。

第五，机制与策略分离。 runtime 提供 fork、call、cancel、join、channel；应用决定 admission、failure policy、effect authority 和结果提交。

第六，并发采用结构化生命周期。 scoped child task 应有明确 parent、取消传播和 join 边界。

第七，长生命周期活动从 frame 中脱离。 CI、后台进程和外部 job 更适合作为 runtime-owned process，通过 typed channel 产生事件。

第八，LLM context 不是 runtime event log。 高频事件需要筛选和压缩，只有真正改变决策的信息才进入下一次 invocation。

第九，不要过早发明新的持久抽象。 如果已有协议机制足以表达行为，先组合已有机制；只有出现稳定、重复的行为契约时，才把它提升为 public abstraction。

结语：Agent 也许更像一台 typed context machine

从最初的问题看，我只是想要一个“不污染主 session 的临时总结”。

但这个小问题暴露出一串更基础的问题：什么是一次 Agent 调用？哪些状态属于 caller，哪些属于 callee？返回值应该去哪？并发 child 由谁拥有？长时间运行的活动应该依附在哪个生命周期上？外部副作用和 conversation frame 是什么关系？为什么一个好的上下文模型还会顺便更适合 KV cache？

沿着这些问题继续推导，我越来越倾向于这样理解 Agent：

LLM Agent
  ≠ conversation + tools

LLM Agent Runtime
  ≈ typed context machine
    + calling convention
    + structured concurrency
    + process/channel model
    + effect authority

在这个模型里，thread 仍然有价值，但它更像 context carrier，而不是整个 runtime 的中心抽象。

真正重要的四个词可能是：

Context
Invocation
Process
Effect

Context 保存模型可见的状态；Invocation 定义 scoped computation；Process 承担长生命周期活动；Effect 明确哪些外部变化需要谁的权限。

如果这些边界能够成立，那么很多今天看起来彼此无关的问题——session 污染、子 Agent、并发、后台任务、事件流、工具权限、KV cache——其实可能只是同一个运行时设计问题的不同表面。

而这也许比再发明一个更复杂的 Agent framework 更值得研究。
