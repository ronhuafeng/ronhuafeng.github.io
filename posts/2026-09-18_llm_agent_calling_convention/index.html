Structured LLM Design：按生命周期组织 Agent Runtime

从一个“不污染主会话的临时总结”出发，讨论如何按生命周期和所有权重新组织 LLM Agent：Context、Invocation、Task、Process 与 Effect，并由此推导 calling convention、KV cache、structured concurrency 与 CSP-style process/channel。

很多 LLM Agent 都从一个很自然的抽象开始：session 或 thread。

它保存 message history。用户继续输入，模型继续回答，工具调用和工具结果也继续追加进去。对于短对话，这几乎没有问题。可一旦 Agent 开始运行较长的任务，thread 往往会悄悄承担越来越多的职责：它既是模型上下文，又像执行轨迹；既保存用户真正关心的历史，又混入临时分析；工具日志、后台任务状态、子 Agent 结果，甚至外部系统的变化，也很容易被继续塞进去。

真正让我开始怀疑这个抽象的，不是什么宏大的架构问题，而是一个很小的需求。

假设我已经和 Agent 工作了很久，现在只想临时问一句：“把到目前为止发生的事情总结一下。”我需要这个 summary，但不希望“请总结”和 summary 本身永久写回原 session。它们只是一次辅助计算，不应该为了完成这次计算而改变被总结的对象。

最初我把这个能力叫作 Stacked Thread：从当前 thread fork 一个临时 child，在 child 中继续若干 turn，拿到结果以后丢掉 child。这个想法来自函数调用栈。

继续推下去以后，我发现问题并不只是缺一个 fork helper。更深的问题是：我们把生命周期完全不同的状态放进了同一个 conversation abstraction。

这篇文章所说的 Structured LLM Design，就是试图重新把这些状态分开。它的核心不是增加更多 Agent 概念，而是一个很普通的软件工程原则：

不同生命周期、不同所有权、不同可见性的状态，不应该因为都和模型有关，就被塞进同一个 session。

沿着这个原则往下走，会逐渐出现五个不同的对象：Context、Invocation、Task、Process 和 Effect。它们并不是预先设计出来的一套分类，而是前一个模型在具体场景里失效以后，被一步步逼出来的。

Conversation 不够表达一次临时计算

先回到 summary。

设当前 context 是：

[A B C D]

最直接的聊天式实现会继续追加：

[A B C D
 User: summarize everything above
 Assistant: ...]

这当然能工作，但语义有些奇怪：为了得到一个 summary，我永久修改了原来的 conversation。

普通函数调用通常不是这样。caller 提供参数和环境，callee 在自己的 activation 中产生局部状态，最后返回一个值。caller 可以选择保存这个值，也可以丢掉它；callee 的内部执行过程不会因为运行过一次，就自动成为 caller 的局部状态。

把这条直觉搬到 LLM runtime，更自然的行为是：

Parent context
[A B C D]
      │
      │ call("summarize")
      ▼
Child invocation
[A B C D] + [local input] + [local execution]
      │
      └── return summary

Parent context
[A B C D]

这里有几个细节必须说准确。

child 从 call time 的 fork point 继承 parent 当时的历史。从这一点以后双方分叉：child 后续 turn 不会 append 回 parent；parent 之后即使继续收到新 turn，也不会自动进入已经存在的 child。parent 并没有因为 child 存在而被冻结，它只是和 child 各自继续。

这已经不是简单的“复制一份聊天记录”。它更像一次 scoped invocation：从 caller context 建立局部执行环境，运行，返回，然后 unwind。

于是我开始觉得，LLM runtime 也许需要自己的 calling convention。

Invocation，而不是第二种 Thread

一旦有了这个想法，一个很诱人的 API 是造一个新的 StackedThread 类型，再给它 Send、SendStream、Close 之类的方法。

我后来认为这正好走反了。

如果底层系统已经有 thread、fork、turn、interrupt、unsubscribe，那么 Stacked Thread 不应该再成为第二套 thread abstraction。它描述的是一次调用关系，不是新的持久身份。

普通语言里也不存在一种 StackedFunction。普通 function 进入一次 call，才产生 activation frame。类似地，一个普通 thread/context 进入 scoped fork-and-run，才形成一次 invocation。

更干净的分层应该是：

Protocol mechanisms
  thread/fork
  turn/start
  turn/interrupt
  thread/unsubscribe

Lifecycle composition
  Continue
  Call
  Fork + first turn

Application patterns
  summarize
  critique
  verify
  what-if analysis
  speculative exploration

协议层保留协议事实，runner/runtime 层组合生命周期，应用层定义用途。这里真正值得抽象的是 Call 的语义，而不是给 Fork 换一个更响亮的名字。

如果落到一个 SDK，我更希望看到类似：

result, err := runner.Call(ctx, CallRequest{
    ParentThreadID: parentID,
    Turn:           turn,
})

一个完整的 Call 应该拥有自己的 scope：在 parent 的 snapshot 上创建 ephemeral child，在 effectful turn 真正开始之前保留 admission boundary，执行并收集结果，取消时中断当前 turn，最后清理 child。

而如果只是让一个已有 thread 再运行一轮，那应该是更普通的 Continue。来源于 fork 并不会让一个 thread 永久变成另一种物种。

到这里，Invocation 出现了：它表示一次有 caller、有局部执行状态、有返回值、有明确结束边界的 scoped computation。

但马上又会遇到下一个问题：Invocation 到底在执行什么？

Context 不是聊天记录，而是执行上下文

calling convention 这个类比之所以没有很快崩掉，是因为现代 Agent 的模型输入本来就不像一串普通聊天文本。

一次调用里可能同时存在 system instruction、developer instruction、user message、assistant message、tool call、tool result、observation，以及各种结构化数据。它们来源不同、类型不同、生命周期也不完全相同，只是最终被组织成一个有顺序的模型可见上下文。

因此，与其把 message list 只看成 history，我更愿意把它看成一种 typed sequential execution context。在一次 invocation 中，它很像 serialized activation record。

编程语言运行时 LLM Agent 运行时
caller frame parent context
call site fork / snapshot point
arguments 本次新增输入
inherited environment 已有 context prefix
locals / temporaries child-local messages、tool traces、observations
return value final result
exception failed / interrupted run
unwind invocation cleanup

这不是说 Transformer 里真的有 CPU 风格的 stack frame。重要的是运行时语义：哪些状态从 caller 继承，哪些只属于本次计算，哪些东西应该返回，哪些东西在 scope 结束后消失。

一旦这样看，另一个长期被混在一起的边界也会显出来：model context 和 program memory 不应该被当成同一块内存。

child invocation 的结果首先应该回到程序：

r, err := Call(ctx, req)
if err != nil {
    // handle failure
}

// 程序决定 r 是否、何时、以什么形式进入某个模型上下文。

这和“把 child 最后一条 assistant message 自动 append 回 parent”是完全不同的设计。前者让程序拥有结果的解释权和提交权；后者直接把模型输出变成 conversation mutation。

这也是我在 llm-go 里那句原则的另一个含义：

Models propose. Programs decide. Effects require authority.

模型可以产生候选结果，程序决定是否接受、验证、排序、保存、合并，或者重新注入某个 context。模型输出不是天然的全局状态变更。

Immutable prefix 不是目标，却是一个很好的副作用

把 invocation 设计成“稳定 caller context + 局部 suffix”以后，还出现了一个意外的工程收益。

假设 parent context 是：

[A B C D]

两个派生调用分别运行：

[A B C D X1 X2]
[A B C D Y1 Y2]

它们共享完全相同的 prefix，只在 fork point 以后拥有自己的 suffix：

             [A B C D]
              /     \
         [X1 X2]   [Y1 Y2]

这恰好也是 prefix cache 或 KV reuse 最容易利用的形态。只要模型、token prefix、运行配置和 serving backend 都支持复用，公共 prefix 就可能共享已经完成的前缀计算，每个 invocation 只需要计算自己的局部 suffix。

这里不能过度承诺。一个语义上 immutable 的 prefix，并不意味着某个具体服务端一定保留 KV。上下文压缩、隐藏 prompt 重写、cache eviction、模型变化都可能导致 cache miss。

真正可靠的说法只是：Structured LLM Design 不主动破坏 shared prefix，因此允许底层实现利用 prefix/KV reuse，而不需要改变上层语义。

这点尤其适合长上下文上的派生计算。一个 100k-token 的稳定 context 可能同时被用于 summary、critique、plan、verification 和 extraction。这些本来就是独立的 sub-computation；如果推理系统能复用公共 prefix，正确的语义边界和高效的计算形态正好指向同一个方向。

到这里，我们有了 Context 和 Invocation。

如果系统永远只有一个同步执行链，这已经相当完整。但 Agent 不会这么听话。

一个 Call Stack 遇到并发就不够了

假设一个 parent invocation 同时启动三个分析：安全性、性能和 API 设计。

                 Parent
               /   |    \
        Security   Perf   API

这时再说“系统只有一个 call stack”就不准确了。完整的 invocation 关系是一棵 tree，而每一个正在运行的 execution strand 都有自己的 active path。

Task A: Root → Parent → Security
Task B: Root → Parent → Performance
Task C: Root → Parent → API Review

换句话说，tree 描述所有 frame 的关系，stack 只描述某一个 task 当前活跃的调用链。

这就是 Task 必须从 Invocation 中单独长出来的地方。

Structured concurrency 解决的不是“并行”，而是 ownership

同时发三个模型请求并不难。难的是谁拥有这三个 child。

parent 被取消时 child 是否取消？一个 child 失败是否终止 sibling？谁负责等待全部完成？如果 caller 已经结束，还有没有孤儿任务在继续烧钱、改文件、拿着 credential 活着？

这些才是 structured concurrency 真正处理的问题。

一个 scoped task group 至少需要明确几个 invariant：child 从创建时的 parent snapshot 开始；parent scope 结束或取消时，默认向 child 传播；child result 先进入 program memory；failure policy 明确属于 caller，例如 fail-fast、wait-all、best-effort 或 first-success。

还有一个对 LLM 特别重要的约束：completion order 不应该自动成为 conversation order。

否则三个 child 谁先返回，谁就先被 append 回 parent，于是：

same inputs
+ different scheduling
= different conversation state

这等于把网络延迟和调度抖动变成了模型语义。

更稳妥的方式是让各 child 返回 typed result，再由确定性的 caller logic 选择顺序、做验证、去重或聚合。只有 caller 决定提交的内容，才进入下一次模型 context。

这也解释了为什么 Stack 这个比喻仍然成立，但必须被放到更大的结构里：

persistent context tree
+ one active stack per task
+ structured task scopes

到这里，Invocation 被扩展成了 Task。

然而 structured concurrency 仍然有一个前提：child 的生命周期属于某个 scope。只要出现一个可能运行几十分钟甚至几个小时的 CI，这个前提又开始松动。

长任务迫使 Task 变成 Process

CI、部署、训练、远程 build、后台服务都有一个共同点：它们可以独立推进，而且可能比创建它们的 LLM invocation 活得更久。

如果强行把这类活动当成普通 child task，就会得到一种很别扭的生命周期：一个模型 frame 为了等 CI 结束而挂十几分钟，期间 progress、heartbeat、log chunk 还不断被塞回 conversation。

这时，Task 已经不够用了。

我更愿意把三种执行形态明确区分开：

形态 生命周期 典型语义
Call / Invocation scoped 调用、返回、unwind
Task scoped concurrent fork/join、取消传播、failure policy
Process 可独立于创建 frame 存在 spawn、events、wait/cancel

Process 不再是某个 conversation frame 的局部变量式执行。它属于 runtime，可以在创建它的 invocation 返回以后继续存在。

这正是 CSP-style process/channel 开始真正有用的地方。

对于一个长时间运行的 CI，更自然的结构是：

caller
   │ spawn
   ▼
CI process
   ├─ Started
   ├─ Progress
   ├─ Output
   ├─ Request
   ├─ Failed
   └─ Completed

调用者拿到的不是“十分钟后的最终字符串”，而是 process handle 或 capability：

type Process interface {
    ID() ProcessID
    Events() <-chan ProcessEvent
    Wait(context.Context) (ProcessResult, error)
    Cancel(context.Context) error
}

CSP 在这里真正提供的启发，不只是“channel 可以异步传消息”，而是另一种状态组织方式：长生命周期活动通过通信暴露变化，不要求某个模型 frame 持续共享和轮询它的内部可变状态。

这也让我重新理解以前更偏事件驱动的 Agent 设计。在 《谁在调用谁：用通信过程和协程理解大语言模型智能体》 里，我更强调 process、channel 和 coroutine，因为长任务确实很难用同步调用链表达。

现在看，这两种模型并不冲突。Call 适合短暂而 scoped 的计算；Task 适合 scoped 并发；Process 适合可以独立推进的长活动。CSP 不是对 call stack 的替代，而是在另一种生命周期上补足它。

LLM context 不应该变成 runtime event log

Process 模型还带来一个直接的上下文设计结论：后台系统产生的大部分事件，不应该进入 LLM context。

一个运行二十分钟的 CI 可能每几秒产生日志和心跳。如果每一次 still running 都被写进 conversation，很快会同时得到 context 膨胀、prefix 不稳定和注意力污染。

更合理的路径是：

Runtime Event Stream
        │
        │ filter / aggregate / select
        ▼
Relevant Observation
        │
        ▼
Next LLM Invocation

原始事件可以完整留在 runtime 中，但只有真正影响判断的信息才进入模型。这与 《从工具调用到事件驱动：大语言模型智能体的运行时架构》 中 observer/planner 的分工是一致的：observer 消费高频 signal，planner 消费经过筛选的语义变化。

有了 channel 以后，Go/CSP 风格的 select 也很自然。runtime 可以同时等待 CI 完成、用户追加输入、另一个 child 返回、timeout 或外部状态变化。谁先 ready，就先处理谁；只有事件需要解释、重规划或产生新 action 时，才重新调用模型。

这时模型更像被 runtime 按需唤醒的 planner，而不是永远占据主循环顶部的“主程序”。

到这里，Context、Invocation、Task 和 Process 都有了各自的位置。

但还有一类状态，始终不肯老实地落进这些 scope。

最后剩下的问题是 Effect

child invocation 可以是 ephemeral 的，task 可以被取消，process 也可以被终止，但文件系统、数据库、网络请求和外部 SaaS 状态并不会因此自动恢复。

这是整个 stack 类比最容易让人误解的地方。

conversation-local state 更像 stack-local state；workspace、数据库和外部系统更像 shared heap 或 external world。函数返回以后 locals 消失，不代表它修改过的全局变量会回滚。Agent 也是一样。

因此：

Frame isolation does not imply effect isolation.

一个临时 child thread 被清理，只说明它的 conversation execution scope 结束了。它在 workspace 中写过的文件、发出的 HTTP request、创建的 cloud resource 可能仍然存在。

这就是为什么 Effect 必须从 Context / Invocation / Task / Process 中单独拿出来。

如果需要更强的隔离，可以引入 read-only capability、workspace snapshot、sandbox、transaction、external mutation approval 等机制。但它们属于 effect system，不应该因为 invocation 恰好是 ephemeral，就被默认假设成“也会回滚”。

这里同样需要 mechanism 和 policy 的分离。runtime 可以提供 interrupt、sandbox、approval callback、transaction boundary；应用决定什么操作允许发生，什么时候需要确认，哪些资源可以访问，什么结果可以提交。

于是那句原则终于完整落地：

Models propose. Programs decide. Effects require authority.

模型负责提出行动和结果；程序拥有 workflow state 和提交决定；外部世界的变化必须经过明确 authority。

Structured LLM Design 最终在结构什么

回头看，这条推导链并不是从一开始就有五个漂亮的方框。

最初只有 Conversation。然后一个“不应该污染原 session 的 summary”说明 Conversation 不够，于是需要 Invocation。

Invocation 一旦被理解成 activation，就要求我们重新理解 Context：哪些是 inherited prefix，哪些是 invocation-local state，返回值为什么应该先回到 program memory。

当多个 invocation 同时存在，一个 call stack 不够，于是出现 Task 和 structured concurrency。

当 activity 可以比 caller 活得更久，Task 的 scope 又不够，于是需要 Process、channel 和 CSP-style communication。

最后，当我们发现某些状态根本不会随着这些 scope 的结束而消失，就必须把 Effect 单独作为共享外部状态来管理。

可以把这条演进写成：

Conversation
    │  无法表达不污染主历史的临时计算
    ▼
Invocation / Call
    │  无法独自表达并发 ownership
    ▼
Task / Structured Concurrency
    │  无法容纳可能超出 caller lifetime 的活动
    ▼
Process / CSP
    │  仍不能解释外部共享状态的权限与回滚
    ▼
Effect Authority

而贯穿这些层级的是 Context。

最终，我会把 Structured LLM Design 描述成下面这组运行时对象：

Context
  模型可见的持久或派生状态
  倾向 immutable prefix + local suffix

Invocation
  一次 scoped computation
  call / return / unwind

Task
  scoped concurrent computation
  structured ownership / join / cancellation

Process
  可以独立推进的长生命周期活动
  spawn / channel / event / wait

Effect
  不随 frame 自动消失的外部状态变化
  explicit authority / policy

这个结构里还有一个很有意思的拓扑对应：

persistent context tree
        ↕
structured concurrency tree
        ↕
KV prefix tree

它们当然不是同一个实现，但都偏好稳定 ancestor、局部 branch 和清楚的 ownership。任意一个正在执行的 task，只是在这棵关系树上的一条 active invocation path，也就是它自己的 call stack。

从 calling convention 的角度，它还可以被进一步理解成一种 LLM execution ABI：caller 提供稳定 context；call boundary 固定 snapshot；新增输入成为 arguments；callee 在局部 suffix 中执行；结果通过明确 return convention 回到 program memory；scope 结束时 frame unwind；外部 mutation 则走独立的 effect authority。

底层 provider 不需要统一实现。一个系统可以用 thread fork，另一个可以用 session snapshot、prompt prefix 或 server-side cache。上层真正需要稳定的是语义：

stable context + scoped computation + structured ownership + explicit communication + explicit effects

这也是为什么我现在不再把最终设计叫作 Stacked Thread。Stack 很重要，但它只解释 scoped invocation 的 active path；Structured LLM Design 试图处理的是更大的问题：如何让 LLM computation 的 context、lifetime、concurrency、communication 和 effects 都有明确结构。

从这个角度看，session 污染、子 Agent、KV cache、并发 fan-out、后台 CI、事件流和工具权限，并不是一堆偶然碰到一起的问题。它们可能只是同一个 runtime design problem 从不同层面露出的几个截面。

而如果这个判断成立，Agent runtime 最值得做的事情，可能不是继续往 session 里塞更多能力，而是开始认真地把它拆开。
