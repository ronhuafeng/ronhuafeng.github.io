Structured LLM Design：从调用栈到并发与进程模型

从一个“不污染主会话的临时总结”出发，逐步形成 Structured LLM Design：把 message list 视为 activation frame，并由此推导 calling convention、immutable prefix、KV cache、structured concurrency 与 CSP-style process/channel。

这篇文章的起点很小。

假设我已经和一个 Agent 工作了很久，当前 session 里积累了大量上下文。此时我只想临时问一句：“把到目前为止发生的事情总结一下。”我需要这个 summary，但不希望“请总结”和生成 summary 的过程永久进入原 session。它只是一次辅助计算，不是主会话本身。

最开始，我把这个能力想成一个 Stacked Thread：从当前 thread fork 一个临时 child，在 child 里继续若干 turn，拿到结果以后丢掉 child。这个名字来自函数调用栈的直觉。

但越往下推，越能发现真正重要的并不是“再造一种 thread”。问题更像是：LLM runtime 是否也需要自己的 calling convention？

一旦从这个角度看，message list、fork、return value、KV cache、并发、CI 这类长任务，甚至外部副作用，开始落到同一张图里。

从一个不该留下痕迹的调用开始

设当前上下文是：

[A B C D]

现在我要基于这段上下文做一次 summary。聊天式系统最自然的做法是继续追加：

[A B C D
 User: summarize everything above
 Assistant: ...]

这当然能工作，但它有一个奇怪之处：为了计算一个 summary，我永久改变了被总结的 conversation。

普通程序不会这样处理函数调用。一个函数可以读取 caller 提供的参数和环境，在自己的 activation 中产生局部状态，最后返回一个值；这些局部执行细节不会因为“函数运行过”就全部变成 caller 的局部变量。

如果把这条直觉搬到 Agent 上，更自然的语义是：

Parent context
[A B C D]
      │
      │ call("summarize")
      ▼
Child frame
[A B C D] + [local input] + [local execution]
      │
      └── return summary

Parent context
[A B C D]

child 从 fork point 继承 parent 当时的历史，然后两边开始分叉。child 里的 turn 不会 append 回 parent；fork 以后 parent 即使继续收到新 turn，也不会自动出现在这个 child 里。parent 并没有被“冻结”，只是这次调用看到的是 call time 的 snapshot。

这个边界比“临时 thread”本身更重要。它说明一次模型计算的内部轨迹和调用者的长期 conversation history，可以是两件不同的事。

到这里，Stacked Thread 这个名字仍然有用，但它更像一个思维入口，而不是应该直接暴露在 SDK 里的新对象。

Message list 不是聊天记录那么简单

函数调用的类比之所以没有很快失效，是因为现代 Agent 的输入本来就不像一串普通文本。

一个 invocation 往往包含 system instruction、developer instruction、user message、assistant message、tool call、tool result、observation，以及各种结构化数据。它们有不同的类型、来源和作用，只是被编码成一个有顺序的 context。

因此，我更愿意把 message list 看成一种 serialized activation record，或者更保守一点，叫作 typed sequential execution context。

传统 stack frame 也不是“一坨内存”。参数、返回地址、保存的寄存器、局部变量和临时值承担不同职责，只是共同属于一次 function activation。LLM context 没有固定的内存 offset，但在运行时语义上存在类似结构。

编程语言运行时 LLM Agent 运行时
caller frame parent thread / context
call site fork point / snapshot point
arguments 本次新增输入
inherited environment 已有 context prefix
locals / temporaries child-local messages、tool traces、observations
return value final result
exception failed / interrupted run
unwind child cleanup / unsubscribe

这个类比真正改变的是我们看待 history 的方式。history 只强调“过去发生过什么”；activation frame 则强调“当前这次计算能看到什么、哪些状态属于这次调用、结果从哪里返回”。

于是一个更清晰的内存边界出现了：

模型上下文和程序状态不应该被当成同一块内存。

一次 child invocation 可以产生结果，但结果首先应该回到 program memory：

r, err := Call(ctx, req)
if err != nil {
    // handle failure
}

// 程序决定 r 是否、何时、以什么形式进入主会话。

这和“把 child 最后一条 assistant message 自动 append 回 parent”是两种完全不同的语义。前者保留了 caller 的控制权，后者则把模型输出直接当成 conversation mutation。

我在 llm-go 里一直采用一句原则：

Models propose. Programs decide. Effects require authority.

放到这里，它不再只是在谈权限。它同时规定了调用边界：模型可以产生候选结果，程序决定是否接受、验证、保存、合并，或者重新注入某个 context。

Fork 不是新对象，调用约定才是抽象

最初想到 Stacked Thread 时，一个很自然的 API 方向是创建 StackedThread，然后再给它 Send、SendStream、Close 之类的方法。

我后来放弃了这个方向。

如果底层协议已经有 thread、fork、turn、interrupt、unsubscribe，再造一套 StackedThread API，本质上是在给现有协议事实换名字，并把两套几乎相同的生命周期同时暴露给调用者。这样的抽象通常不是更简单，只是多了一层要记住的东西。

更合适的分层是：底层保留协议事实，上层只组合生命周期。

Protocol mechanisms
  thread/fork
  turn/start
  turn/interrupt
  thread/unsubscribe

Lifecycle composition
  Continue
  Fork + run
  scoped Call

Application patterns
  summarize
  critique
  verify
  what-if analysis
  speculative exploration

如果把它落到 SDK，我更希望看到类似下面的接口：

result, err := runner.Call(ctx, CallRequest{
    ParentThreadID: parentID,
    Turn:           turn,
})

Call 的价值不在于替调用者藏掉一个 Fork 方法名，而在于它拥有一个完整的 scoped lifecycle：从 parent 的 fork point 创建 ephemeral child，在真正开始 effectful turn 之前保留 admission boundary，执行并收集结果，在取消时中断当前 turn，最后 unwind child。

而一个已经存在的普通 thread 如果只是需要继续跑一轮，则应该由更通用的 Continue 一类机制处理。这里没有必要把“来自 fork 的 thread”永久升级成另一种身份。

这个区别很像函数和 stack frame：语言里没有 StackedFunction 这种特殊函数类型。普通 function 进入一次调用，才有一个 activation frame。

为什么最后还是可以叫 stack

单纯的 fork 其实是 tree branching，不是 stack。

真正让 stack 语义成立的是嵌套调用。A 调 B，B 再调 C；C 返回以后回到 B，B 再调用 D。完整关系是一棵 call tree，但任意同步执行时刻只有一条 active path：

A
A → B
A → B → C
A → B
A → B → D
A → B
A

所以更准确的说法是：context 的持久结构可以是一棵 tree，而一个 task 当前活跃的 invocation chain 是 stack。

这也是我现在仍然愿意保留 “Stacked” 这个词的原因。它描述的不是某种新的 thread 数据结构，而是调用关系。

一个意外的好处：它和 KV cache 的结构相容

走到这里，我才意识到，这套语义还有一个很实际的系统优势：它鼓励稳定、不可变的 context prefix。

设 parent context 是：

[A B C D]

两个独立调用分别产生：

[A B C D X1 X2]
[A B C D Y1 Y2]

逻辑上，它们共享同一个 prefix，只在 fork point 以后拥有自己的 local suffix：

             [A B C D]
              /     \
         [X1 X2]   [Y1 Y2]

这恰好也是 prefix cache 或 KV reuse 喜欢的结构。只要模型、token prefix、运行配置和 serving backend 都允许复用，公共部分就有机会共享已经完成的前缀计算，而每个 branch 只计算自己的 suffix。

这里要非常克制。这种 calling convention 不保证 KV cache 一定命中。 服务端可能做上下文重写、compaction、cache eviction，甚至根本没有暴露可复用的 server-side cache。语义层能保证的只有一件事：不主动破坏 shared prefix。

这已经足够有价值。

因为一个长 session 很可能同时需要 summary、critique、plan、verification、extraction 等多个派生计算。如果这些任务都从相同的稳定 prefix 开始，它们在语义上是独立 sub-computation，在支持 prefix reuse 的实现里也正好拥有可共享的计算前缀。

换句话说，这里不是“为了 cache 扭曲 API”，而是正确的调用边界和高效的推理形态碰巧朝同一个方向走。

但 frame 隔离不等于副作用隔离

这个类比也有一个必须说清楚的边界。

child 的 conversation timeline 可以是局部的，文件系统、数据库、网络和外部服务却未必是。

函数返回以后，局部变量消失，但它对 heap 或外部世界造成的修改不会自动消失。Agent invocation 也是一样：ephemeral child 被清理，并不意味着它改过的文件、发出的请求或创建的资源会回滚。

所以 conversation frame 更像 stack-local state，而 workspace 和外部系统更像 shared heap / external effects。

这也是为什么 effect authority 必须和 invocation isolation 分开。read-only capability、workspace snapshot、sandbox、transaction、外部 mutation approval 都可以存在，但它们属于 effect system，不应该被偷偷包装进“临时 child”这个概念。

并发让“一个 stack”不再成立

同步调用很容易让人沉迷于 call stack 这个比喻，直到第一个并发需求出现。

假设 parent 同时启动三个分析：安全性、性能和 API 设计。此时系统里不可能只有一个 active stack。更准确的结构是：所有 invocation 形成一棵 context tree，而每个并发 task 都有自己的 active path。

                 Parent
               /   |    \
        Security   Perf   API

这一步自然把问题带到 structured concurrency。

并发最难的从来不是“同时发三个模型请求”。真正麻烦的是 ownership：谁负责取消 child，谁等待它们结束，失败是否传播，返回顺序是否有语义，parent 结束以后还有没有孤儿任务。

如果 child 属于一个 scoped invocation group，那么几个默认约束会变得很自然：child 从 call time 的 parent snapshot 开始；parent scope 取消时，取消向下传播；child 结果在 program memory 中汇合；failure policy 由 caller 明确选择，而不是被 SDK 偷偷决定。

其中有一条尤其重要：completion order 不应该自动变成 conversation order。

否则，同一组输入仅仅因为网络延迟不同，就可能得到不同的 parent history：

same inputs
+ different scheduling
= different conversation state

这等于把调度抖动升级成语义。更稳妥的做法是让 child 各自返回 typed result，再由 deterministic caller logic 排序、筛选、验证和合并。

到了这里，stack 仍然存在，但它已经不再是整个 runtime 的唯一结构。更准确的组合是：persistent context tree + one active stack per task + structured task scopes。

长任务逼着我们离开调用栈

再往前一步，structured concurrency 也不够。

CI、部署、训练、远程 build、后台服务可能运行几分钟甚至几小时。让一个 LLM frame 为了等 CI 结束而一直活着，不只是资源模型别扭，还会诱导系统不断把 progress、log 和 heartbeat 塞回 conversation。

这类活动和普通 child call 有本质区别：它们可能比创建它们的 invocation 活得更久。

我现在更愿意明确区分三种执行形态：

Call 是一次 scoped computation。它有明确的 caller，完成后返回一次，然后 unwind。

Task 是 scoped 的并发 child。它属于 structured concurrency scope，需要 join、取消传播和显式 failure policy。

Process 则是 runtime-owned 的长生命周期活动。它可以独立推进，甚至在创建它的 LLM frame 已经结束以后继续存在。

这也是 CSP-style process/channel 开始真正有用的地方。

对于一个长时间运行的 CI，更自然的接口不是“阻塞十分钟等函数返回”，而是启动一个 process，然后通过 typed events 观察它：

caller
   │ spawn
   ▼
CI process
   ├─ Started
   ├─ Progress
   ├─ Output
   ├─ Request
   ├─ Failed
   └─ Completed

调用者拿到的更像 capability 或 process handle：

type Process interface {
    ID() ProcessID
    Events() <-chan ProcessEvent
    Wait(context.Context) (ProcessResult, error)
    Cancel(context.Context) error
}

这里真正值得借鉴的不是“channel 很适合异步”这种泛泛结论，而是 CSP 的通信观：长生命周期活动通过消息暴露状态，不要求某个 conversation frame 持续持有并轮询它的内部可变状态。

这也修正了我以前更偏事件驱动的一种表述。在 《谁在调用谁：用通信过程和协程理解大语言模型智能体》 里，我更强调 process、channel 和 coroutine，因为长任务确实很难被同步调用链描述。现在看，CSP 并没有取代函数调用，它只是覆盖了另一种生命周期。

短暂、scoped 的计算适合 Call；scoped 的并发适合 Task；独立推进的长活动适合 Process。把三者全部叫成一个模糊的 AgentRun，反而会让最关键的 ownership 消失。

LLM context 不应该充当 runtime event log

Process 模型还解决了一个很实际的问题：后台系统产生的大部分事件根本不值得进入模型上下文。

一个运行二十分钟的 CI 可能每几秒输出日志。如果 Agent 不断把 still running、heartbeat 和普通进度写回 conversation，很快会同时得到三个问题：context 膨胀、prefix 变得不稳定、模型注意力被低价值信号占用。

更合理的链条是：

Runtime Event Stream
        │
        │ filter / aggregate / select
        ▼
Relevant Observation
        │
        ▼
Next LLM Invocation

这与我此前在 《从工具调用到事件驱动：大语言模型智能体的运行时架构》 里讨论的 observer/planner 分工是一致的。原始 runtime event 可以被完整保留，但模型只应该看到足以改变判断的那部分。

有了 channel 以后，Go/CSP 风格的 select 也成为一个很自然的 runtime 控制原语：系统可以同时等待 CI 完成、用户追加输入、另一个 child 返回、timeout 或外部状态变化。哪个事件先准备好，runtime 就先处理哪个；只有当事件需要解释和重新规划时，才再次调用模型。

模型于是更像一个被 runtime 唤醒的 planner，而不是永远占据“主程序”位置的中心循环。

最后得到的不是一个新 Thread，而是一套 execution model

回头看，最开始那个“临时总结一下 session”的小需求，最后把问题一路推到了 runtime architecture。

我现在会把这套模型概括成下面几层：

Context
  persistent immutable-prefix tree

Invocation
  stack-based calling convention

Scoped concurrency
  structured task tree

Long-lived activity
  CSP-style process + channel

Effects
  explicit authority over shared state

其中有一个结构上的对应尤其值得保留：

persistent context tree
        ↕
structured concurrency tree
        ↕
KV prefix tree

它们当然不是同一个东西，但它们都偏好稳定的 ancestor、局部的 branch 和清楚的 ownership。任意一个正在执行的 scoped task，只是这棵关系树上的一条 active path，也就是它自己的 call stack。

如果继续抽象，这甚至可以被看成一种 LLM execution ABI：caller 提供稳定 context；call boundary 固定 snapshot；本次输入成为 arguments；callee 在局部 suffix 中执行；结果通过明确的 return convention 回到程序；frame 在 scope 结束时 unwind；外部 effect 则遵守独立的 authority 规则。

底层实现不必统一。某个 provider 可以用 thread fork，另一个可以用 session snapshot、prompt prefix 或 server-side cache。真正应该保持稳定的是上层语义：

stable caller context + scoped local execution + explicit return + explicit effects。

这也解释了为什么我现在不太想把最终抽象叫作 Stacked Thread。这个名字很好地描述了最初的直觉，却没有覆盖并发和长生命周期 process。

更完整的图景可能是：

                     Program
                        │
          ┌─────────────┴─────────────┐
          │                           │
   Invocation Runtime           Process Runtime
          │                           │
     Call / Task                 Spawn / Channel
          │                           │
   stack / fork-join          long-lived activity
          │                           │
          └─────────────┬─────────────┘
                        │
                  Result / Event
                        │
                        ▼
                 Program decides

对我来说，真正值得继续研究的已经不是“如何给 thread 增加一个 fork helper”，而是四个更基础的对象：Context、Invocation、Process、Effect。

Context 决定模型能看到什么；Invocation 定义一次 scoped computation；Process 承担可以脱离调用帧继续存在的活动；Effect 规定哪些外部变化需要什么 authority。

从这个角度看，session 污染、子 Agent、并发、后台任务、事件流、工具权限和 KV cache 并不是一堆互不相关的问题。它们很可能只是同一个 runtime 设计问题，从不同层面露出的几个截面。

而这比再发明一个名字更响亮的 Agent framework，至少有意思得多。
