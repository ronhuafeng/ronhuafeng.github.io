Harness Engineering：模型之外的工程

AI agent 的可靠性不只取决于模型能力，也取决于工具、权限、验证、观察和人工确认构成的运行环境。

Harness EngineeringAISoftware Engineering

当 AI agent 开始进入真实工作流，问题就不再只是“模型够不够聪明”。模型能力当然重要，但系统能否可靠工作，还取决于模型之外的一组条件：它能看到什么，能调用什么工具，哪些操作必须确认，结果怎样验证，失败以后谁来发现和恢复。围绕这些条件建立起来的工程实践，可以称为 harness engineering。1

这个词也说明了 AI 工程重心的一种变化：从只优化单次模型输出，转向设计模型运行的条件。过去，人们很容易把系统表现直接归因于模型：提示词写得好，回答就更好；模型更强，系统似乎也会更可靠。但 agent 不只是回答问题。它会读文件、调用工具、修改代码、发送请求，还可能连续执行很多步骤。到了这一步，仅靠模型自己的判断已经不够，外部运行环境也必须承担责任。

Harness engineering 关心的正是这个外部系统。它不是简单的提示词技巧，也不是给模型加一层包装界面。这项工程涉及工具接口、权限边界、记忆机制、验证流程、观察日志、回滚机制、任务分解、人工确认点，以及失败后的处理方式。换句话说，它设计的不是某一次回答，而是模型行动的条件。

传统软件当然也有不确定性。并发、外部服务、用户行为和硬件故障都可能让执行结果偏离预期，软件工程早就用接口、状态机、重试和失败处理来应对这些问题。

Agent 多了一层麻烦：不确定性也来自行动者本身。同一个目标，它可能选择不同路径；同一段上下文，它也可能得到不同解释。于是问题不再只是“怎样写出确定规则”，而是“怎样让一个不完全确定的行动者在可控环境中完成任务”。工程要求没有降低，只是需要约束的对象变了。

好的 harness 既不能放任模型，也不能把它锁死。约束太少，agent 可能误读任务、滥用工具，甚至把一个局部错误扩大成外部后果；约束太多，系统又会变得僵硬，模型的推理和适应能力发挥不出来。真正困难的是划边界：哪些地方可以让模型探索，哪些地方必须由程序、策略或人工确认来收口。

例如，在代码场景里，agent 可以自己读仓库、提出修改、运行测试，但不能因此直接获得生产部署权限。它可以编辑文件，关键变更却仍要经过 diff 审查。它可以调用搜索工具，但结论需要保留依据。它也可以生成解决方案，但结果仍要经过测试、静态检查或人工确认。

这些安排不会让模型突然变聪明，却会直接改变一次错误能够造成什么后果。模型还是那个模型，只是被放进了一个更可靠的执行结构里。

从这个角度看，harness engineering 的核心不是控制模型说什么，而是规定模型在什么条件下行动。它依据什么信息？能调用哪些工具？做到哪里必须停下来？失败以后怎样被发现和恢复？

因此，系统能力不能只看模型本身。在需要持续工具调用、权限控制和结果验证的工作流里，一个能力稍弱但运行在良好 harness 中的模型，可能比更强却缺少约束和验证的模型更可用。真实工作需要的不只是答案，还需要证据、边界和责任链。

Capability、Authority 与 Validation 是三件不同的事

当 agent 开始真正改变外部世界时，有三个问题很容易被混在一起：它能不能做、它现在可不可以做，以及做完以后我们凭什么接受结果。

Capability 回答的是“系统能做什么”。如果系统向 agent 暴露了读仓库、执行命令、发送邮件这些工具，说明这些能力存在，但不代表每一次调用都被允许。

Authority 或 policy 回答的是“这一次可不可以做”。同一个 capability，会因为用户授权、资源范围、风险等级或当前任务不同而得到不同决策。权限边界管理的是具体行动，而不是工具是否存在。

Validation 回答的是“做完以后，凭什么相信结果”。命令成功退出，不等于目标已经完成；部署接口返回成功，也不等于服务已经健康。测试、状态读回、交叉验证和人工审查，都是 validation。

把这三件事分开，harness 的责任就清楚了：模型可以提出行动，程序决定是否接受；外部变化需要明确授权；执行完成以后，还要独立验证结果。可以把这条原则写成：

Models propose. Programs decide. Effects require authority.

这与 《Structured LLM Design：按生命周期组织 Agent Runtime》 中对 Effect 的区分是同一个边界的另一面。那篇文章讨论 computation 如何存在、通信和结束；这里讨论这些 computation 在什么权限、验证和风险条件下可以影响外部世界。

这些安排也在分配权力。Harness 决定 agent 能接触什么信息，哪些来源被信任，哪些操作被允许，哪些风险必须优先拦住。它不只是技术基础设施，也在定义模型能够看到什么、能够做到什么。

因此，这些选择最好是可见的：信息来源可以追溯，权限边界可以审查，失败过程可以追踪，异常结果可以纠正。否则，组织里的偏见、盲区和惯性很容易被一起写进系统。

因此，harness engineering 不是“让 AI 自动化一切”的技术。它更像一套责任分配机制：哪些任务交给模型，哪些判断留给人，哪些步骤由程序验证，哪些失败必须中断流程。它既利用模型的推理和探索能力，也限制错误能够扩散到多远。

在 agent 系统中，模型能力和 harness 质量已经是两个可以独立变化的工程变量。更强的模型不会自动带来更清楚的权限边界，也不会自动产生可靠的验证、观察和恢复机制。反过来，好的 harness 也不能替代模型能力。真正可用的系统需要把两者配合起来，稳定地把模型能力转化为可以检查、可以限制、也可以恢复的行动。

这正是 harness engineering 的意义：它把关注点从“模型这一次答得怎么样”扩展到“模型在什么条件下工作”。生成能力本身不足以保证可靠性；工具、权限、观察、验证和恢复共同决定了 agent 能否在复杂系统中持续工作。

Footnotes
